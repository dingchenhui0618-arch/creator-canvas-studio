# 压测：10 个并发到底会不会 OOM（v0.9.73，2026-11-14）

## 一、结论先行

B2 里一直缺的那句「10 个并发会不会 OOM」，现在有两个答案，两个都要说：

1. **会 —— 旧代码上，10 个并发评审第 17 秒把进程打死了。**
   单图 17.9 MB（旧代码对素材没有任何上限）、闸门关掉、10 个账号同时提交：V8 堆顶到 384 MB 上限，
   `FATAL ERROR: Reached heap limit Allocation failed - JavaScript heap out of memory`，进程直接退出。
   10 个请求全部断开（`NETWORK`），健康探针 5.1 秒无响应、11 次失败。这就是「所有人的会话一起断」的真身。
2. **现在不会了 —— v0.9.73 加了两道入口闸之后。**
   10 个并发提交、单图 8 MB、全站上限 3 条：**3 条进来、7 条被拒（503 `SERVER_BUSY`）**，堆峰值 **110 / 408 MB（27%）**，
   健康探针 p95 **114 ms**，实例存活，跑完名额全部还回。被拒的 7 条不扣积分、不落任务、不调上游。

上限 **3 条** 的依据（同一天、同一台机器、同一套脚本量的）：

| 场景 | 堆峰值 | 结果 |
| --- | --- | --- |
| 3 并发 · 单图 8 MB | 110 / 408 MB（27%） | 全部成功，探针 p95 129 ms |
| 10 并发 · 单图 8 MB · **闸门关掉**（最坏情况） | 332 / 408 MB（81%） | 全部成功，但水位自动进 `tight`（8 次采样） |
| 10 并发 · 单图 17.9 MB · **闸门关掉** | 393 MB（上限 384） | **FATAL OOM，进程退出** |

复刻那条路的瓶颈不在堆，在 **ffmpeg 子进程**：3 条并行时子进程合计 277 MB，10 条并行时 **921 MB（≈92 MB/条）**，
而整台机器只有 1866 MB、生产常驻 ~90 MB。这就是「上限不能拍成 10」的第二个理由。

顺带挖出并修掉两个「一个请求就能打死进程」的入口：**请求体没有上限**（9 MB 的 JSON 会整段读进内存再解析）、
**评审素材没有类型与大小校验**（指到数据目录里的 160 MB 源视频就是一次 OOM）。生产上三条用例实测
**415 / 413 / 413**，余额 **9950 → 9950**（都在扣费之前被拒）。

## 二、怎么量的

脚本：`scripts/loadtest.mjs`（本轮新增，`npm run loadtest`）。它自己起一辆**一次性的完整实例**（独立 `DATA_DIR` / 端口 /
`--max-old-space-size=384`，与生产一致），不碰生产、不碰真实上游：

| 环节 | 做法 | 为什么这么做 |
| --- | --- | --- |
| 上游 | 本地假上游，按 `--upstream-ms` 故意慢 4 秒，一次返回同时满足视觉分析与视觉评审的 JSON | 让任务真的叠在同一时间窗里，而不是排队；一分钱不花 |
| 请求 | 真 `POST /api/review` / `POST /api/replicate`，真过闸门、真扣积分、真落库 | 量的必须是线上那条路，不是模拟函数 |
| 抽帧 | 复刻那条路真的下载视频、真的 spawn ffmpeg（`ffmpeg-static`） | 复刻的内存大头在子进程，假不掉 |
| 读数 | 每 250 ms 采样：**进程树 RSS（含子进程）**、V8 堆（读实例自己的 `/api/admin/waterline`）、系统 `MemAvailable`、闸门在跑数、假上游并发 | 「用了多少」和「还剩多少」是两件事，一起量 |
| 探针 | 每 300 ms 打一次 `/api/health`，记 p50 / p95 / 最慢 | 内存没炸但主线程被打死，用户照样用不了 |
| 判定 | 脚本自己判（`evaluate`）：闸门开时放进来超过上限、被拒原因不是名额满/水位红线、实例死了、名额没还回、出现 500、探针最慢 > 5 s —— 任一条算不通过 | 压测不能靠人眼看「好像还行」 |

两个让测量不变形的处理：

- **每账号一条请求**（评审按账号只放 1 条并行），**把 `X-Forwarded-For` 打散**：入口限流（每分钟 10 次）和并发闸门不是一回事，
  混在一起量出来的是限流，不是容量。
- 两个臂（开/关闸门）都跑：**开闸门**回答「生产现在会不会死」，**关闸门**回答「上限该定几条」。

## 三、实测（同一台机器：2 核 / 1866 MB / 堆上限 384 MB / Node 22.12.0）

| 臂 | 场景 | 请求结果 | V8 堆峰值 | 进程树峰值 | 健康探针 p95 / 最慢 |
| --- | --- | --- | --- | --- | --- |
| `r3-2m5` | 评审 3 并发 · 2.5 MB | 3 / 3 成功 | 44 MB（11%） | 162 MB | 48 / 87 ms |
| `r3-8m` | 评审 3 并发 · **8 MB（新上限）** | 3 / 3 成功 | 110 MB（27%） | 314 MB | 129 / 154 ms |
| `a` | 评审 3 并发 · 17.9 MB（旧代码允许的量级） | 3 / 3 成功 | 229 MB（56%） | 504 MB | 463 / 933 ms |
| `r10on` | 评审 **10 提交** · 8 MB · **闸门开** | **3 进 / 7 拒**（`SERVER_BUSY`） | 110 MB（27%） | 315 MB | 114 / 181 ms |
| `d` | 评审 10 提交 · 17.9 MB · 闸门开 | 3 进 / 7 拒 | 228 MB（56%） | 506 MB | 331 / 479 ms |
| `r10-2m5` | 评审 10 并发 · 2.5 MB · 闸门关 | 10 / 10 成功 | 116 MB（28%） | 282 MB | 114 / 215 ms |
| `r10-8m` | 评审 10 并发 · 8 MB · 闸门关 | 10 / 10 成功 | **332 MB（81%）** | 677 MB | 697 / 748 ms |
| `c` | 评审 10 并发 · 17.9 MB · 闸门关 | **10 / 10 断开**（进程死） | 观测到 225 MB，GC 日志 393 MB | 811 MB | **5119 ms / 11 次失败** |
| `e` | 复刻 10 提交 · 闸门开 | 3 进 / 7 拒 · 3 / 3 跑完 | 20 MB（5%） | 385 MB（**ffmpeg 277 MB**） | 76 / 78 ms |
| `f` | 复刻 10 并发 · 闸门关 | 10 / 10 跑完 | 26 MB（6%） | **1036 MB（ffmpeg 921 MB）** | 280 / 337 ms |

三条从数据里直接读出来的事实：

1. **评审吃的是堆，不是子进程**：单图越大，堆越高（2.5 MB → 11%，8 MB → 27%，17.9 MB → 56%）；同一条路 10 个并发直接把堆顶穿。
2. **复刻吃的是子进程**：堆只有 20-26 MB，ffmpeg 每条 ~92 MB；10 条并行时系统可用内存从 ~1115 MB 掉到 **642 MB**。
   机器 1866 MB、生产常驻 ~90 MB —— 这时只要有人再跑一条别的重活，就开始和 swap 抢（这台机器 swap 已用 1.8 GB）。
3. **主线程被打死时，内存可能还没到红线**：`c` 组观测到的最后一个堆读数是 225 MB（55%），进程却在 393 MB 时死了；
   同一时间健康探针已经 5.1 秒没响应。所以「只看内存百分比」不够，探针延迟是另一条独立信号。

## 四、上限 3 条怎么来的，什么时候能放宽

两道闸是互补的，缺一个都出事：

- **单请求上限（8 MB）** 管「一次请求最多能吃多少」：把最坏情况从「一个请求 160 MB」压到 8 MB 量级；
- **全站并发上限（3 条）** 管「同一时刻有几个字节持有者」：8 MB × 10 = 81%（水位紧），8 MB × 3 = 27%（余量充足）。

放宽到 10 条并发的三条路（都不在本轮范围）：

1. **把评审图先缩到 1600px 再发给模型**：3 并发 17.9 MB 时堆已到 56%、探针最长 0.93 s —— 缩图能把这部分直接砍掉一个数量级；
2. **worker 隔离**：ffmpeg / 出图放进独立进程或有内存上限的 cgroup，炸的是它，不是 API 进程；
3. **换机器或加第二台**：按实测，10 条复刻并行需要 ~1 GB 子进程内存，1.86 GB 的机器上不该放开。

## 五、压测顺手挖出的两个真问题（本轮修掉）

### 1）请求体没有上限

`server/routes/_shared.mjs` 和 `server/index.mjs` 各有一份 `readBody`：**把整个 body 读进内存再 JSON.parse**，67 处调用点共用。
一个 100 MB 的 JSON 请求体 = Buffer + UTF-16 字符串 + 解析结果三份 —— 384 MB 的堆直接见底。
公开入口（前端异常上报、反馈）也走同一个函数，**不需要登录**就能发。

修法（`server/body-reader.mjs`）：三道闸，从便宜到贵 ——

1. `content-length` 声明就超了：一个字节都不读，直接 413；
2. 读到一半超了：不再往数组里拼（内存不再涨），把剩下的流读完再拒，客户端才收得到 413；
3. 超过 4 倍上限：断连接 —— 到这一步这客户端不是在传 JSON，是在灌数据。

67 处调用点一处没改（`routes/_shared.mjs` 只是把导出转发过去）。拒绝走 `refusalResponse()`：**4xx 是我方拒绝，不是 500**，
日志记一条 `request.refused`，不去触发 5xx 告警。

### 2）评审素材没有类型与大小校验

`routes/review.mjs` 的 `readLocalMedia` 以前只校验路径在 `DATA_DIR` 里，然后 `fsp.readFile` 整个读进来；
未知扩展名还会被当成 `image/jpeg` 继续往下走。指向数据目录里的**源视频（最大 160 MB）**就是一个请求打穿进程。

修法（同一个文件）：扣费与占名额**之前**先 `probeLocalMedia()` ——
只认 jpg/png/webp（否则 **415 `MEDIA_TYPE`**）、文件大小 > 8 MB 直接拒（**413 `MEDIA_TOO_LARGE`**，连字节都不读）、
文件不在或不是普通文件（**404 `MEDIA_MISSING`**）、路径跳出数据目录（**400 `MEDIA_PATH`**）。
外部图片地址那条路也从「整段 `arrayBuffer` 下来再判 8 MB」改成「先看 `content-length`、边读边卡」。

## 七、边界

- **假上游**：只回固定 JSON、固定延迟。量的是入口、内存与闸门，不是模型准确率，也不是真实上游耗时。
- **单机单进程**：并发计数仍在进程内。多进程 / 多机部署时这一层不是全局的（B2 剩下的那半）。
- **图是生成的**：内容不重要，字节数与解码开销才重要；尾部填充出来的图不是可解码的合法 JPEG（服务端不解码，只 base64 转发）。
- **RSS 求和会重复计共享页**：所以进程树 RSS 与系统 `MemAvailable` 两个数都给；判断机器还剩多少，看 `MemAvailable`。
- **采样 250 ms**：进程被杀的最后一瞬可能采不到（`c` 组观测到 225 MB，GC 日志里的 393 MB 才是致死点）。
- **没测 `flow_run`**（画布运行走网关出图/出视频，要真实上游额度）。按「同样吃堆 + 上游等待」估算与评审同量级，但没有实测。
- **Windows 本机只能冒烟**：`/proc` 采样不可用，脚本会标 `memory.source = unavailable`；容量数字只在 Linux 生产机上有效。

## 八、怎么复跑

~~~bash
# 本机冒烟（只验证脚本与闸门逻辑，量不到 RSS）
node scripts/loadtest.mjs --kind=review --n=3 --guard=on --upstream-ms=2000

# 生产机上（一次性的完整实例，加内存上限的 cgroup，炸也炸不到生产）
cd /opt/visionqa && systemd-run --scope -q -p MemoryMax=1300M -p MemorySwapMax=0 \
  --unit=vq-lt-recheck /usr/local/bin/node scripts/loadtest.mjs \
  --kind=review --n=10 --guard=on --upstream-ms=4000 --image-mb=8 \
  --data-dir=/tmp/vq-lt-recheck --out=/tmp/vq-lt-recheck.json --label=recheck

# 只看这一层的单测
node --experimental-sqlite --experimental-strip-types --test test/loadtest.test.mjs test/body-limit.test.mjs test/review-media.test.mjs
~~~

退出码：0 = 符合预期；1 = 有一条预期没满足（脚本会列出是哪条）；2 = 压测本身没跑起来。
