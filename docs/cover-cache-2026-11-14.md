# 封面抓一次就够，抓不到也有话说（v0.9.90，2026-11-14）

## 结论

`/api/cover` 以前是纯透传：每个请求各自去上游抓一次，整段读进内存（上限 8MB）。
一屏模板库 40 张封面、翻两次页就是 80 次上游请求；两个人同时翻，内存里十几份整图。
这台机器 2 核 / 1.86GB，撞上这个慢的是所有人的页面，极端时直接 OOM。

现在三层，各管一件事：**同一张只抓一次**（进程内 LRU + 60 秒负缓存）、
**一个账号每分钟最多抓 120 次**、**整机同一刻最多 4 张在上游**（满了先排 5 秒再拒）。
响应多一个可观测的 `X-VQ-Cover: hit|miss|limited|busy|bad`；前端封面抓不到时
退回卡片自己的占位文案，不在网格里留破图。

生产实测同一张小红书封面：部署前两次都 468ms / 245ms（各自回源），
部署后 443ms 首抓、之后 **3–5ms 命中**，字节数前后都是 **213,152 B**、sha 一致。

## 改了什么

- **`server/cover-cache.mjs`（新）**：三个纯状态机。
  - `createCoverCache`：进程内 LRU，条目（64）与字节（24MB）双上限、10 分钟过期、
    「抓不到」的负缓存 60 秒；正片与 404 分开存，一张坏封面不会把一张好封面挤出去。
  - `createWindowLimiter`：按账号的固定窗口（每分钟 120 次），账号表超过上限先清过期桶。
  - `createSemaphore`：整机名额，满了排队等，名额**直接转交**给排队最早的那个（不是先还再抢）。
- **`server/cover-proxy.mjs`（新）**：编排三层，并把 `fetchImage` 做成可注入的——
  单测因此不需要网络就能量「同一张抓了几次」「同时几张在上游」。
  429/503/404 一律 `no-store`，429/503 带 `Retry-After`。
- **边读边数**：以前是 `await response.arrayBuffer()` 之后再量大小，一张 500MB 的图
  会先被完整读进内存，那个 8MB 上限等于没写。现在先看 `Content-Length` 提前放弃，
  没有就以 8MB 为界边读边断。
- **`src/components/CoverImage.tsx`（新）**：封面加载失败（含 429 / 503）时退回占位文案。
  记的是「哪一张失败了」而不是一个布尔，换了一条内容就自然复位，不用 effect。
- **配置**：`VQ_COVER_PER_MINUTE`(120) / `VQ_COVER_CONCURRENCY`(4) / `VQ_COVER_WAIT_MS`(5000) /
  `VQ_COVER_CACHE_ENTRIES`(64) / `VQ_COVER_CACHE_MB`(24) / `VQ_COVER_CACHE_TTL_MS`(10 分钟) /
  `VQ_COVER_NEGATIVE_TTL_MS`(60 秒)。写 0 = 关掉对应那一层，退回 v0.9.89 的纯透传。

## 七条坑

1. **用 `unref()` 的计时器兑现的 Promise，会永远挂着**：本机 Node 24 全绿，
   CI 的 Node 22.12.0 上三条名额用例报 "Promise resolution is still pending but the
   event loop has already resolved"。服务进程一直有活所以线上看不出来，测试把它露出来了。
   排队等待这 5 秒不值得为它埋一个「偶尔永远等下去」。
2. **「读进内存再量大小」的上限等于没写**：`arrayBuffer()` 之后再判断 8MB，
   那张 500MB 的图已经进内存了。要先看 `Content-Length`，再边读边断。
3. **负缓存必须与正缓存分开**：混在一张表里，一张 404 会把一张真图挤出去；
   反过来把 404 存成「200 空图」，卡片上就是一张空封面而不是一句说明。
4. **缓存命中不能吃限流**：否则「翻回上一页」也会被拒。上限的语义是
   「一分钟去上游抓几次」，不是「一分钟看几次封面」。
5. **分享页的限流对象是链接本身**：按账号算，一条公开链接就能被无限刷；
   按 token 算，哪条链接热就限哪条。
6. **429 / 503 必须 `no-store`**：被浏览器存住就变成「刷新也没用」，
   客户端还会把它当永久失败。给 `Retry-After`，人知道过一会儿再来。
7. **测试要能数「上游被调了几次」**：没有这个可数事实，缓存与限流都只能靠感觉。
   所以 `fetchImage` 是注入的，假抓取器同时记录调用次数与并发峰值。

## 发现但没做

- **缓存仍在进程内**：两个实例（8799 / 8800）各有一份，各算各的名额。
  跨进程共享要先有共享存储，为封面图引入它不划算——画布那种花钱的活才值得。
- **封面不落盘**：进程重启后第一次仍要回源一次。换成对象存储/本地磁盘缓存是另一件事。
- **没有域名白名单**：任何公网图片都能被代理（内网地址已被 `fetchPublic` 挡住，
  但「代理任意图床」这件事本身没限）。真正的白名单要运营给出平台清单。
- **Referer 规则还是两条正则**（小红书 / 抖音）+ 原样 origin，新平台要改代码。

## 边界与回退

分享页、交付包、打印页的封面照旧可读（分享 token 就是凭证）；本地演示
（`VQ_REQUIRE_AUTH=0`）不受影响；`VQ_COVER_*=0` 可以逐层关掉退回纯透传。
回退：`bash /opt/visionqa/ops/rollback.sh --to 2`（v0.9.89）——这一轮没动 nginx，
不需要还原配置。
