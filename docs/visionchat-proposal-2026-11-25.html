VisionChat（Beta）方案

日期：2026-11-25 · 基线：v0.9.285（master，未提交工作区）· 状态：方案待拍板，未动代码
参考：用户仓库 dsh-chatroom（https://github.com/dingchenhui0618-arch/dsh-chatroom）、Pachat 公开文档（https://pachat.ai）
纪律：本文只写方案。没有改 src/、server/、package.json；没有调用任何真实上游；所有关于现有能力的描述都能在仓库里指出文件。

结论先行

  1. VisionChat 做「房间」，不做第二个 Pachat。 平台侧是登录后的多智能体聊天室：一个房间里有 1 个人 + N 个智能体（后续可加人），智能体是成员而不是工具。Pachat 解决的是跨平台 agent 之间的异步通信（每只 agent 自己的 token、收件箱、长轮询唤醒），那套东西我们不抄，只借它「群聊 + 提及 + 幂等键」的产品直觉。
  2. 入口放在「模板库」下面，作为一级导航第 5 项，沿用 src/nav.ts 已有的 chip: 'Beta' 机制（工作流就是这么标的），不改工具区。
  3. 智能体「操控 CLI」在平台侧先落成「白名单工具」，不是服务器 shell。真正的本机命令执行已经存在（Electron 本地工作区：读目录/读文件免批准，写文件/改文件/执行命令逐次批准、命令 60 秒、路径锁在工作区内），平台版复用它验证过的审批 + 副作用分级模型，但不把 shell 搬到公网服务器上。
  4. 连接方式选 SSE + 事件序号 + 服务端回合，不用 WebSocket。放弃的是「广播级实时」和「在线状态」，换来的是与现有 /api/chat/.../messages/stream（已带 X-Accel-Buffering: no）、nginx 300 秒超时、2 核 1.8G 单进程部署相安无事。
  5. 计费按「对话回合 1 次 + 每次工具调用各 1 次」，全部走已有 charge/refund，先扣后调、失败全退、ref 可对账；权限先只读、写操作逐次审批，默认不给「完全授权」。

1. 定位与边界

是什么

项定义
产品形态平台内的多智能体聊天室（房间制），Beta
成员人（当前账号）+ 从 agents.json 拉进来的智能体；一期不开多人，二期开同工作区成员
消息房间内按 seq 单调递增，支持提及、引用回复、分页翻历史
智能体有名字与职责（进每次提示词）、各自独立会话、可被点名或按规则轮次发言
工具平台白名单能力（读模板库 / 读工作流 / 网页读取 / 生图 / 生视频 / 视觉评审），带审批与计费

不是什么

不做原因
不做 Pachat 式「agent 自带 token 从平台外接入」Pachat 的模型是平台外的 agent 用自己的 pachat_ token 收发消息；我们是登录后的单一平台，账号体系已经存在（vq_session + sessions 表），再叠一层 agent 身份只会带来两套权限真源
不在服务器执行任意命令（shell）公网服务器 + 多租户 = 一个提示词注入就能拿到宿主；本机 CLI 留在桌面端
不做公网房间码/匿名加入与「必须登录 + 积分」冲突；一期只做登录态房间，邀请走链接 token（三期）
不做语音/视频通话、附件（一期）与当前聊天室的最小闭环无关

和「快捷创作」里的对话有什么区别（这一条最容易讲混，必须讲清）

维度快捷创作 · 对话（已上线）VisionChat · 房间（新）
参与者1 个账号 + 1 个平台模型1 个账号 + N 个智能体，后续可加人
上下文单条长会话，服务端按 token 预算截断 + 摘要每个智能体各自的会话；房间消息是共享上下文
谁在说模型具名成员：每条消息标「谁说的」
触发用户发一句，模型回一句提及必回 / 全员轮次 / 主持人，可并行开关，但有预算闸门
工具联网搜索、读链接、思考模式（模型侧）平台工具（模板、工作流、生图、评审），由服务端执行并计费
计费每轮 chat 1 积分每轮 chat + 每次工具调用各自的价目
数据DATA_DIR/chat/<账号>/<会话>.json，最多 30 会话 / 每条 200 消息 / 单条 32000 字需要 seq、成员、未读、分页，文件形不够用（见第 6 节）

4. 「智能体可操控 CLI」怎么落地

先对齐词：用户说的「CLI/工具」，在平台侧应当理解为可执行的白名单工具。已有两套事实：

  • 桌面端真 CLI：electron/agent/tools.mjs 的工具集是 list_dir / read_file / search_text（无副作用、免批准）、write_file / edit_file / run_command（needsApproval: true，逐次批准）；命令 60 秒超时、输出截断 8000 字、路径锁在工作区根内（resolveInside）；loop.mjs 每轮最多 8 步，批准由宿主注入，拒绝即 fail closed；密钥只留在服务端（/api/local-agent 用平台 Key 换一次补全）。
  • 平台侧工具：AGENT_TOOLS 里只有「对话前读一次模板/工作流/网页」和「把回复里的 JSON 抽出来」，没有模型发起的工具调用循环，image-gen 至今是 planned —— 也就是说，「智能体自己决定调用工具」这件事当前并未实现。

推荐模型（一期只落一颗钉子：只读 + 一个写操作）

层设计与现有代码的关系
工具注册表服务端一张表：id / label / scope(只读/读写) / needsApproval / creditKind / 参数 schema / 执行函数扩展 AGENT_TOOLS，不另起第二份能力清单
只读工具读模板库、读工作流、网页读取（仅公开 http/https，沿用 webread.mjs 的字节与字数上限）、导出 JSON（把回复里的 JSON 块整理成可下载文件）自动执行，结果注入下一步上下文；不扣积分
写操作（一期只开一个）生成一张图：参数只收「提示词 + 尺寸 + 参考资产 id」，走 /api/media/generate 同一套上游与限流该工具已有服务端实现，只差房间侧调用与审批
审批房间级档位：只读（默认）/ 写操作需批准 / 完全授权（仅房主可开，二期）；批准人 = 房间成员，二期扩到「房主可代批」抄 dsh-chatroom 的三档与 fail closed：不点、超时 90 秒、服务重启或档位被改成只读，一律按拒绝收尾
越权智能体只能调用「房间为它勾选的工具 ∩ 平台已 ready 的工具」；参数在服务端按 schema 校验，模型给的多余字段丢弃不信任模型输出，与 electron/agent/tools.mjs 把路径限制在工作区是同一个思路
计费每次工具调用一条 charge，ref = room:<roomId>:call:<callId>；失败 refund 同 ref；工具卡显示这笔账outstandingCharge 已能保证「同一 ref 不会多退」
失败上游失败、参数不合法、超时 → 工具卡标失败并全退；不写进消息正文冒充结果与 media-gen 现有退款口径一致

明确不做：服务器上的 shell、任意 URL 抓取（只允许公开页面且过 SSRF 校验）、写文件、改数据库、调用管理接口。若用户要的是「真的在我机器上跑命令」，答案在桌面端本地工作区，不在 VisionChat。

5. 连接方式对比

方案延迟服务端代价与现部署的关系断线恢复实现成本
轮询（每 2–3 秒拉一次）2–3 秒每客户端每 2 秒一次请求；2 核 1.8G 下 50 个房间 = 每秒 25 次查询，SQLite 读写会被放大无特殊要求，nginx 无感天然从 seq 续拉，不重不漏最低
SSE（推荐）亚秒级每客户端一条长连接；单进程 Node 下几百条可承受，但每条都占一个 socket 与一段内存/api/chat 与 /api/flows 已在用，带 X-Accel-Buffering: no；nginx proxy_read_timeout 300s，心跳 15 秒即可安全穿过用 Last-Event-ID / ?since= 从 seq 续传低（复用 sseWrite 那一套）
WebSocket亚秒级需要 http 升级处理；反向代理要额外配置；Node 单进程下连接数与心跳管理更重现在没有任何 WS 代码；nginx 与 Caddy 两套部署都要改需要自定义重连与补洞协议高

推荐：SSE + 服务端回合 + seq 续传，轮询作为降级（EventSource 连续失败 3 次 → 切 /messages?since= 每 3 秒轮询，界面顶部提示「实时连接断了，正在用轮询」）。放弃的是：不做「谁在线」的实时 presence（轮询下会闪），不做 <200ms 的多端同步；这些在 Beta 都不值当。

容量边界（写进验收）：单房间同时 1 个回合在跑（与 dsh-chatroom 的「一轮一人一次」同源）；全局并发复用 config.credits.concurrency.chat = 2 的闸门，超了返回 429 并说明「还有对话在跑」；SSE 单账号最多 2 条连接，服务端拒绝第 3 条并给原因。理由：2 核 1.8G 上真正贵的是模型调用，不是连接；把闸门放在模型入口最省钱。

回合调度（服务端，不依赖客户端在线）：

  1. 人发一条消息 → 落库 seq = n，同步返回；
  2. 调度器按房间规则选出本轮要发言的成员（提及必回 / 全员一轮），用「本轮预算」封顶（建议默认最多 2 个智能体回合、深度 1，比 dsh-chatroom 的 3/2 更保守，因为每次都是真扣费）；
  3. 每个成员按顺序跑：拼上下文（房间最近 N 条 + 该成员自己的历史 + 工具上下文）→ 调模型 → 落库 seq = n+1 → SSE 推送；
  4. 45 秒无回应落一条失败占位（可只重试该成员）；「停止本轮」清空队列并作废旧回合（用世代号，抄 dsh-chatroom 的做法）；
  5. 用户中途插话：排队到本轮结束再处理，不丢。

6. 存储与数据形状

现有 chat-store.mjs 是「一个账号一个目录、一条会话一个文件」，并明确写了「两者的数据形状不一样，硬塞进一个文件只会让两边都难改」。房间需要 seq 连续、成员外键、未读游标、工具调用与积分对账，文件形做不到原子追加与分页查询，因此新建 SQLite 表（数据库已经是 node:sqlite 的 DatabaseSync，见 server/auth.mjs；建表沿用 CREATE TABLE IF NOT EXISTS 的做法）：

表关键列说明
roomsid, name, owner_id, rules_json, approval_mode, created_at, dissolved_atrules_json 存「提及必回 / 全员一轮 / 预算」；解散不删，置 dissolved_at（墓碑）
room_membersid, room_id, kind, user_id, agent_id, name, role, joined_at, removed_at（kind 取 human / agent）智能体成员引用 agents.json 的 id，不复制 systemPrompt
room_messagesid, room_id, seq, sender_member_id, body, mentions_json, reply_to, state, created_at（state 取 ok / failed / tool）UNIQUE(room_id, seq)；一张表同时存人的话、智能体的回复、系统通知
room_tool_callsid, room_id, message_id, tool, args_json, status, credit_cost, ledger_ref, artifact_id, created_atledger_ref 与 credit_ledger.ref 对上，积分可对账
room_readsroom_id, member_id, last_seq未读数 = 最新 seq − last_seq；不做已读回执给对方看

保留口径：每房间最多 4000 条（超出滚动归档），投影给前端最近 200 条、分页每页 100 条 —— 与 dsh-chatroom 的 200/4000/100 相同，理由同样是不让一次打开房间把全历史读进内存。

6.1 与现有 chat-store 的关系

  • 不迁移、不改写：DATA_DIR/chat/ 是「快捷创作」的一对一会话，VisionChat 另建表；两边互不读对方数据。
  • 命名不撞：房间接口全部挂 /api/rooms，不复用 /api/chat 前缀，避免将来两套消息语义混在一个路由里。
  • 备份口径一致：房间表落在现有 SQLite 文件里，跟着已有的备份脚本走；不新增第二个数据库文件，减少运维面。
  • 回滚：表是新增的，回滚先把入口从导航摘掉（src/nav.ts 一处），接口与表留着不碍事；Page 类型与 pageLabels 的条目可以留一版再删，避免同一次提交里改动面过大。这一点要求一期不写任何「房间消息 → 作品/模板」的单向搬迁，二期再加。

7. 安全

面措施失败时
房间成员鉴权每个房间接口先查 room_members 且 removed_at IS NULL；不是成员 403，不返回房间是否存在403 + 一句中文原因
消息归属发送者由服务端从 currentUser 决定，请求体里的 sender 一律忽略；智能体消息只能由调度器写入客户端伪造无效
工具越权工具白名单 ∩ 房间勾选 ∩ 账号可用；参数按 schema 校验；只读工具不碰写路径；写工具必须过审批拒绝并落一条 denied 工具卡，不产生扣费
提示词注入工具结果、网页正文、他人消息都按「不可信数据」处理，进上下文时明确标注来源与边界，不让模型把消息内容当指令；服务器侧没有任何「消息里出现某指令就执行」的路径最坏是回复被带偏，不会执行动作
审批伪造审批记录写服务端（谁、哪条调用、什么时候、允不允许）；审批只能由有权限的成员发起，客户端不能自称已批准fail closed，超时 90 秒按拒绝
限流新接口单独开桶：房间发送 20 次/分钟/账号、工具调用 6 次/分钟/账号（与 ratelimit.mjs 的 60 秒滑动窗口同机制；IP 桶作为第二道，防换号）429 + 重试秒数
审计room_tool_calls 即审计：谁、在哪个房间、调了什么工具、花了多少积分、结果如何；管理员在后台可查，普通成员只能看自己房间不可删除，只追加
邀请（三期）一次性 invite token，绑定房间与席位，有效期 7 天；不做房间码（房间码适合无账号的 LAN，我们有账号）过期/用掉即失效
隐私房间消息不进入公开分享页；分享作品时只带产物，不带对话正文——

8. 分期与验收

一期：能开会话的房间（约 1 个迭代）

范围：导航入口 + 房间 CRUD + 成员（人 + 智能体）+ 消息流 + @ 必回 / 全员一轮（默认只开第一个）+ 服务端回合 + SSE 推送 + chat 计费 + 只读工具 4 个 + 失败占位与「重试该成员」+ 未读与历史分页。 不做：他人加入、写操作工具、附件、悬浮窗、移动端独立布局。

验收（全部可测）：

  • 两个智能体同房，@ 谁谁回；一条消息最多引出 2 个回合，超出不再发言；
  • 一轮之内同一成员只说一次；插话排队不丢；停止本轮后旧回合迟到的事件被丢弃；
  • 断线 30 秒重连，消息按 seq 不重不漏；EventSource 失败 3 次后切轮询且有提示；
  • 每轮扣 1 积分、失败退 1；credit_ledger 里能找到 room 的 ref，余额 = 流水求和；
  • 非成员访问房间返回 403/404；另一个账号读不到该房间的任何消息；
  • 390 宽不横向溢出，间距只出现 4/8/12/16/24/32，无 emoji 图标。

二期：工具调用与审批

范围：工具注册表、工具调用卡、审批三档（默认只读）、生图（一个写操作）、生视频与视觉评审、产物回填与「引用到作品」、管理员审计页。 验收：发起生图 → 卡在「待批准」→ 拒绝则 0 扣 0 执行；批准 → 扣 5 积分 → 成功出图并回填 artifact_id → 失败全退；审批超时 90 秒按拒绝；模型消息里写「调用 run_command」不产生任何执行；单账号工具调用超 6 次/分钟返回 429。

三期：多人、邀请与运营

范围：同工作区成员加入、邀请链接、只读访客、房间模板（把一条作品/模板变成房间的初始任务）、房间回收站。 验收：邀请令牌一次有效；被邀请者 7 天内加入且席位唯一；访客只能读与 @ 自己的智能体；解散后历史保留、输入锁住；管理员可导出某房间的审计 CSV。

8.1 风险与观测

风险触发条件缓解观测指标

9. 需要拍板的问题（6 条）

  1. 「CLI」到底指什么：平台白名单工具（推荐），还是必须能在你的服务器上跑真命令？后者要单独的安全方案，我不建议放进 VisionChat。
  2. 入口位置：按用户原话放「模板库」下面（推荐，Beta 标签）；还是并进工具区（与快捷创作、无限画布并列）？
  3. 一期开不开多人：只做「1 个人 + N 个智能体」（推荐，一期风险最小），还是直接做同工作区多人？
  4. 工具分期：一期只上 4 个只读工具、生图放二期（推荐）；还是把生图压进一期？生视频与视觉评审每次 15 / 5 积分，建议更靠后。
  5. 计费口径：一条消息扣 1 次 chat（推荐，与桌面端「一轮一次」一致），还是按每个智能体回合各扣 1 次？
  6. 默认授权档位：房间默认「只读」、写操作逐次批准（推荐）；要不要给房主一个「完全授权」开关，开了之后不再逐次问？
