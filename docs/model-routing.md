# 平台模型 Key 路由：选谁、为什么、刚才走的谁

这份文档说明三件事：**一次模型调用怎么选出 Key**、后台怎么**预演**这次会走哪把、
以及怎么查**刚才那次调用**到底走了哪把、为什么、多快、成没成。

适用代码：`server/keyvault.mjs`（决定与日志）、`server/chatcall.mjs`（真实调用）、
`server/routes/admin.mjs`（后台接口）、`src/pages/admin/ModelRoutePanel.tsx`（后台界面）。

## 一、选择顺序

对每次调用（能力 + 模型）依次判定：

1. **只考虑启用的 Key**，并且它声明了本次要的能力（`text` / `vision` / `image` / `video`）。
2. **模型白名单**：调用指定了模型时，声明了白名单但不含该模型的 Key 跳过；
   没有声明白名单的 Key 视为「通用」，任何模型都能用。
3. **冷却**：连续失败 3 次的 Key 冷却 60 秒，冷却期间跳过；任意一次成功立刻解除。
4. **优先级**：剩下的 Key 里取优先级数字最小的一组（数字越小越先用）。
5. **权重**：同一组内按权重随机（权重只影响概率，不改变组）。
6. **兜底**：池里一把可用的都没有时，回落到环境变量里的旧凭证；
   环境变量也没配，调用直接失败并回 `NO_MODEL`，不假装成功。

第 4、5 步是「为什么要按权重」容易误解的地方：权重不会让低优先级的 Key 抢队，
只有同优先级的几把之间才按权重分流。

## 二、后台能做两件事

### 预演：现在调一次会走哪把

```http
POST /api/admin/model-keys/preview
{ "capability": "text", "model": "deepseek-flash" }
```

返回每把 Key 的状态（`eligible` / `disabled` / `capability` / `model` / `cooling`）与原因、
同优先级组里每把的选中概率，以及一句结论：

```json
{
  "description": "现在调用会用「DeepSeek 官方（原环境变量）」（优先级 P100）。",
  "group": [{ "name": "DeepSeek 官方（原环境变量）", "state": "eligible", "share": 100 }],
  "keys": [{ "name": "DeepSeek 官方（原环境变量）", "state": "eligible", "reason": "可选" }]
}
```

**预演和真实调用用的是同一份判定代码**（`planRoute`），所以不存在「后台说走 A、实际走了 B」。

### 决策日志：刚才那次走了哪把

```http
GET /api/admin/model-keys/routes?limit=50
```

每条记录包含：时间、能力与模型、Key 名称与 id、判定理由、尝试次数、耗时、成败、错误结论。
汇总给出总次数、成功 / 失败、回落环境变量次数、平均耗时，以及按 Key 的聚合。

注意：日志存在进程内存里（最近 200 条），**重启后清空**。界面上写明了这一点。
需要跨重启保留时再落盘，现在不为排障数据引入磁盘写入。

## 三、日志里记什么、不记什么

记：能力、模型名、Key id / 名称、来源（Key 池 / 环境变量 / 无可用 Key）、判定理由、耗时、成败、错误结论。

不记：**Key 明文**、请求正文、对话内容、用户身份。单测里有两条断言专门守这件事
（`scripts/test-keyvault.mjs`、`scripts/test-model-routes.mjs`）。

## 四、错误结论的写法

上游报错不直接丢给管理员，先归类成人话，原始报文留在 `detail` 里悬停可看：

| 上游情况 | 后台显示 |
| --- | --- |
| `Insufficient Balance` / `insufficient_quota` | 额度不足（HTTP 402） |
| `invalid api key` / 401 / 403 | 凭证无效（HTTP 401） |
| 429 / `rate limit` | 上游限流（HTTP 429） |
| `finish_reason=length` | 输出被截断 |
| 5xx / 超时 / 连接失败 | 上游暂不可用（HTTP 5xx） |

这样「换个模型还是失败」和「换把 Key 就好」在后台能一眼分开。

## 五、怎么验

单测（不联网、不花钱）：

```bash
node scripts/test-keyvault.mjs     # 预演判定、日志聚合、人话报错、无明文
node scripts/test-model-routes.mjs # 假上游跑真实调用链路：成功留痕、失败留痕
```

线上（管理员）：

1. 打开后台「模型 Key」页，在「路由预演」里选能力、填模型，点「预演路由」；
2. 去发起一次真实对话或评审，回到「最近路由」点刷新，应出现刚那次调用的记录；
3. 记录里的「走的是哪把」应当与预演结论一致。

## 六、还没做

- **按账号 / 业务线分流**：现在全平台共用一个池，没有「这个用户走这把 Key」的能力。
- **成本视图**：只记耗时与成败，没有 token 与费用统计（上游返回的 usage 还没落库）。
- **持久化**：日志不跨重启。
- **Key 级限速**：只有失败冷却，没有主动限流。
- **出图 / 视频真实调用**：路由已支持这两类能力，但画布出图通道还没接到这个池，
  目前只有文本与视觉会真的产生路由记录。
