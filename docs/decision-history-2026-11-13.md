# 拍板记录回看：多版、旧结论、已失效都留着（v0.9.26）

**结论**：作品页的「评审」里多了一块「拍板记录」——这条作品名下每一次拍板都按时间倒序排着，每行写清第几版、那次评审模型说了什么、当时为什么放行，并且逐条标出它**还算不算数**：管这一版 / 这一版重评过、已失效 / 早先那一版。旧记录不再是「改判或撤销之后就消失」——它是记录，不是开关。配套把「撤销」修准：撤销只拿走这一版这一次评审的那条，早先几版的记录留着；要连历史一起删是「清空拍板记录」，点两下才动手。顺带修掉两处旧毛病：没有 `ownerId` 的老拍板以前谁都撤不掉、还会在历史里印两遍；管理员也撤不掉别人拍的那条。

- 版本：`0.9.26`；发布包 `20261112-195749-v0.9.26-decision-history.tar.gz`；入口 `index-Ce2mVQZq.js`。
- 提交：`待填`；CI run `待填`；测试 `284/284`，oxlint `0 error / 6 warning`，构建通过。
- 生产实测：真实拍板一次 → 记录出现 1 条「管这一版」、胶囊变「评审 · 人工通过」、下一步变「交付这一版」；撤销这次拍板 → 记录归零、胶囊回到「需人工确认」、队列仍是 1 条待办。一来一回之后 `decisions: 0 / decision: null`，数据与入口核对过，没有留下任何东西。

## 一、这一轮补的是哪块空

v0.9.21 给「人工复核」加了一层：模型给结论，人拍板；同一版再评出新结论，拍板自动失效、这条回到待办。逻辑是对的，但界面只显示**当前这一版有效的那一条**——旧的那几条在数据里，页面上看不见。于是开新版（或这一版重评）之后，人就再也答不出「上一版我为什么放行」「那次我是不通过还是没拍」。

队列里那句「你拍板过 N 条 · 最近：…」也只写最近一条，点进作品页看到的还是只有当前这一版。这一轮把「拍板」当成有历史的记录：留着、写清、并标明还算不算数。

## 二、三种「还算不算数」

服务端在返回作品详情时给每条拍板加一个 `state`（与状态胶囊读的 `decisionFor` 同一口径，页面不自己再算一遍）：

| state | 什么时候 | 页面写 |
| --- | --- | --- |
| `current` | 这条拍板的 `reviewAt` 就是当前这一版最近一次评审 | 管这一版 |
| `stale` | 同一版，但那次评审后来又被评过 | 这一版重评过 · 已失效 |
| `past` | 早先某一版的拍板 | 早先那一版 |

- 版次 0（版本划分之前留下的记录）折进 v1——与评审、运行、交付那几处的口径一致。
- 没有当前评审（新版还没评过）时，谁都不算 `current`：不硬挑一条当现行。
- `decision` 不是「通过 / 不通过」的记录不往历史里排（数据坏了就少显示一条，不显示一条假判断）。

## 三、三个决定

1. **状态算在服务端，页面只负责写人话**。胶囊、下一步、交付稿、评审对照纸与这块历史读同一份判断；页面自己再算一遍迟早会分叉。`decisionHistory()` 是纯函数（`server/project-status.mjs`），10 条用例把三种状态、版次折叠、空输入、坏记录都钉住。
2. **撤销 ≠ 清空历史**。`DELETE /api/reviews/decision/<id>?reviewAt=…` 只拿走那一次评审的拍板（作品页的「撤销这一版」）；不带 `reviewAt` 才是整条作品的记录清空（「清空拍板记录」）。清空要点两下：第一下按钮变成「再点一次：清空 N 条」，5 秒没有第二下自己缩回去。
3. **覆盖与撤销都按「看得见」算（`canAccess`）**。原来按 `ownerId` 硬比，留下两个毛病：没有 `ownerId` 的老记录谁都撤不掉（登录账号看着有按钮，删的是 0 条），而且同一版同一次评审会堆出两条拍板、历史里印两遍；管理员也撤不掉别人拍的那条。现在统一成「能看见才撤得掉、才覆盖得掉」——与列表、队列、评审那一套一致。

## 四、界面

- 位置在「人工复核」卡片下面、评审列表上面：它是这一页里第二次出现的结论，所以压在评审明细之前、拍板动作之后。
- 每行：结论胶囊（人工通过 / 人工不通过）+ 版次 + 状态 + 时间与那次评审的模型结论 + 备注；评审还在列表里的行可以点进去看当时的证据原图（`→`），不在列表里的行只读，不给假链接。
- 底部一行说清两件事：「撤销只拿走这一版；早先几版的记录留着。」右边是「清空拍板记录」（点两下才动手）。
- 窄屏（≤640px）换一种排法：胶囊与版次、箭头在第一行，正文独占第二行——不把 11px 的说明挤成一条缝。
- 撤销过的作品，卡片回到「模型结论：需人工确认 · 还没人拍板」，这块历史里留下的是更早的那几条——「撤销」不会连历史一起吃掉。

## 七、验收清单

- [x] 多版拍板都看得见：管这一版 / 这一版重评过 / 早先那一版三种状态，一条作品里同时出现。
- [x] 撤销只拿走这一版这一次评审的那条；早先几版的记录还在。

- [x] 状态由服务端算，与胶囊 / 下一步 / 交付稿同一口径；纯函数 10 条用例。
- [x] 没有 ownerId 的老记录：撤得掉、覆盖得掉，且不会堆成两条。
- [x] 窄屏换行不挤、不横向滚动。
- [x] 生产只读核对 + 一次往返实测，两头都核对过数据（归零）。

## 八、边界

- 只记「拍板」，不记「已看过」：看过的便利贴仍然只显示当前这一版，做历史要另开一轮（它不改结论，价值不同）。
- 每个账号最多留 200 条拍板（沿用旧上限，超出挤掉最早的）——不是无限档案库。
- 行只能点进「评审还在列表里」的那次证据（列表最多 20 条评审）；不在列表里的行只读。
- 不按人分组：单账号产品，一条作品只有一类拍板人；多人协作要等账号体系真用起来。
- 不导出拍板历史成 CSV；交付稿与评审对照纸仍按版次各印各的。
- 撤销后不能「重做」上一次撤销：要恢复就再拍一次（会是一条新记录，时间也是新的）。
