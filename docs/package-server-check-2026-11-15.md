# 封存包的另一头：服务器上那一份也自己查（v0.9.128，2026-11-15）

## 问题

v0.9.127 让用户在本机核对下载回来的 zip，但没有人核对**服务器上封存的那一份**：包被截断、被覆盖、盘被清掉、恢复备份时拿错文件——档案里的哈希仍然写着 `8558a630…`，下载下来却是另一个东西。等到收件人对不上再来查，已经说不清是哪一步坏的。封存只做了一半：写下了「当初是什么」，却没检查「现在还是不是」。

## 做法

- **stat**：作品详情顺手带上 `package.disk = { present, bytes }`，每条封存包一次 stat，只读元数据，不算哈希。
- **流式哈希**：新增只读路由 `GET /api/projects/:id/delivery-packages/:pid/check`，`createReadStream` + `createHash` 边读边算，不把 64 MB 整份塞进内存。
- **纯函数判分**：`packageIntegrity(record, actual)` → `{ ok, state }`，state 分 `ok` / `mismatch` / `resized` / `missing` / `unverifiable`；单元测试只测它，不碰磁盘。
- **界面**：核对面板下半段是「服务器上封存的那份」——盘上大小胶囊 +「查一遍哈希」；档案行只在不对劲时给一句红字，并把「下载包」换成「包没了」，不给人一个点了就 404 的按钮。
- **健康检查**：`/api/system/health` 多一项「交付封存包」，全量 stat（最多 200 条，不算哈希），丢一份就 warn。

边界：只读、不缓存、不清文件、不改档案；封存包仍只认登录态，不走公开分享。哈希开销只发生在有人点「查一遍」的那一次。

## 踩坑

1. **同 URL 的 hash 导航不会重新取数**：`Page.navigate` 到同一个 `#/projects/<id>` 不触发刷新，界面还拿着旧数据，点「核对」反而把面板收起来。要 `Page.reload({ ignoreCache: true })`。
2. **深健康检查是 `/api/system/health`**（登录可见），`/api/health` 只回答「配了没配」；拿错路径时 packages 一项直接是 null。
3. **生产数据在 `/var/lib/visionqa`**，不是 `/var/lib/visionqa/data`；写错路径会把「1 作品 3 评审 9 运行」读成全 0。
4. **release.sh 把标签截到 24 字符**：`20261114-202055-r138pkgcs` 落盘成 `20261114-202055-r138pkgc`，glob 要按截断后的找。
5. **胶囊字号不能写 10.5px**：`test/design-grid.test.mjs` 卡「微标签 11px 起」，第一次全量测试因此失败；改成 11px 重新构建、重新部署。

## 发现但没做

- 不校验 ZIP 内部 CRC、不逐条解压：整包哈希已经覆盖内容。
- 公开的 `/api/health` 没加这一项：丢包是内部事实，不挂到探针上；真要做巡检告警还缺告警 webhook（用户尚未提供）。
- 没有定期巡检与告警推送；没有下载次数 / 保留期 / 异地备份。
- 生产仍是 0 条交付、0 个封存包，所以生产侧验到的是部署、版本、哈希、401 与公开字节；核对的两头只在本地真 Chrome 验过。
- 手机上只有点选，没有拖放。

## 回退

`bash /opt/visionqa/ops/rollback.sh --to 1` → **v0.9.127**；`--to 2` → **v0.9.126**。服务端只加一个只读路由与一个纯函数，不改数据结构、不需要迁移；回退后旧前端不会请求 `/check`。
