# 快捷创作：手机上整页滚，输入框贴在屏幕底部（r222 / v0.9.206）

日期：2026-11-18

## 问题

r221 把会话列表收成一条之后，回答区从 48vh 提到 58vh，但手机上**输入框还在回答区下方**：
页面头部（标题 + 方式页签 + 对话方式）本身约 300px，844 高的屏要看到输入框得往下滚，滚下去又看不到回答。
用户的原话是「至少让我看得清楚字是啥」——打字这件最基本的事不该要滚。

## 改法

| 项 | 改前 | 改后 |
| --- | --- | --- |
| 谁在滚 | 回答区自己滚（58vh 小窗） | **整页滚**（文档级） |
| 输入框 | 在回答区下方，走出屏幕 | **sticky 贴屏幕底部**（bottom 8px），一直可见 |
| 回答区高度 | 上限 58vh | 不限高，读到哪算哪 |
| 滚到底 | — | 底部留 272px `scroll-margin`，最后一段不会被输入框挡住 |
| 手机版头 | 标题 + 说明两行 | 标题 22px、说明收进空状态（只在 ≤560 生效） |
| 输入框本身 | 241px 高（含 Ctrl+Enter 提示） | **201px**：手机上藏掉 Ctrl+Enter 那行、文本域 56px、去掉拖拽手柄 |

### 关键是先放开 `.vq-content` 的 overflow

sticky 贴不住底的原因不在按钮，在祖先：`.vq-content` 写了 `overflow: auto`。按 CSS 规则，
**只要祖先有滚动框，哪怕它从不滚动，也会成为 sticky 的参照**——它的滚动位置永远是 0，
所以按钮跟着内容一起走（r221 实测：文档滚到 620px 时，按钮 top=899，已在屏幕外）。

窄屏（≤900）本来就是文档级滚动（shell 在那一档设了 `height: auto; overflow: visible`），
于是这一档把 `.vq-content` 的 `overflow` 也放开成 `visible`：参照回到视口，按钮才贴得住。
真会横向撑开的容器（表格、代码块、后台表格）各自有自己的 `overflow`，不受影响——
这条改动在 390 / 320 两档、9 个页面上逐页量过，页面级横向滚动一处都没有（见下）。

## 验收（本机临时实例 + 假上游 + 无头 Edge，0 次真实上游调用、0 元）

3 条会话，回答含标题/列表/表格/引用，390×844 实测：

| 位置 | 输入框 top / bottom | 在视口内 | 最后一段回答 bottom |
| --- | --- | --- | --- |
| 空状态（未选会话） | 595 / 836 | 是 | — |
| 展开列表 | 595 / 836 | 是 | — |
| 选完会话（自动滚到底） | 595 / 836 | 是 | 539（在输入框上方，没被挡） |
| 滚到页面顶端 | 595 / 836 | 是 | 1511（在下方，继续往下读） |
| 滚到中途 520px | 595 / 836 | 是 | 991 |

- 回答区高度：**1144px**（改前固定在 490px），整页滚；`innerWidth = scrollWidth = 390`。
- 输入框高度：**201px**（改前 241px）；`position: sticky`。
- 滚到文档最底（2001px）时输入框不再贴底：那时看到的是页面下方的「对话预设」卡片库，
  不在对话面板里——这是有意的，不是失效。
- 横向溢出扫描：390 / 320 两档 × 9 个页面（工作台、爆款雷达、模板库、作品、快捷创作、工作流、运行记录、视觉评审、设置），
  `document.documentElement.scrollWidth` 全部等于 `innerWidth`，页面级横向滚动 0 处。
- 1440：输入框 `position: static`、回答区上限 56vh、版头与说明照旧、左栏 240px——桌面一点没动。

## 边界

- 手机上输入框常驻占 201px（约一屏 24%）：工具行（联网搜索/读链接/思考模式/附件）在 390 宽会折成两行，
  再压就得把它们收进菜单，属于下一步的产品决定。
- 平台对话时，页面下方仍然列着「对话预设」卡片库（既有结构）：页面因此很长，滚到卡片区时输入框自然松开。
  要不要在平台对话时把卡片库收起来，等真的有人抱怨再定——那会动到「从对话直接切预设」的入口。
- 展开状态不记忆；桌面仍是回答区自己滚（56vh），没有跟进 sticky。
- 只改样式 + 一个空 div 的 class，没有新接口、没改服务端、没动计费。
