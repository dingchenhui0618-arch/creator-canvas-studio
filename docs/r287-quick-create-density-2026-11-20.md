# r287：快捷创作先减负；对话框直连生图/生视频的接法先对齐（v0.9.269）

日期：2026-11-20 ｜ 前置：r286 / v0.9.268

## 一、快捷创作为什么显得挤（看了真实页面才敢动手）

在用户自己的 Chrome（1366×768、已登录生产）打开 `#/agents` 看的：

- 屏上有 **三排控件**：① 对话 / 图片 / 视频；② 平台对话 / 对话预设 + 一行能力说明；
  ③ 联网检索 / 读链接 / 思考模式 / 附件；
- 同一批能力被说了 **三遍**：空状态卡片的四条说明、「对话方式」那行文字、下面那排开关；
- 输入框底下一行密到 11–13px：`Enter 发送 · Shift + Enter 换行 · 附件最多 5 个（图片 2 张）、单个 8 MB`，
  右边还挂一个「3 项能力已打开」。

1366 宽、768 高的机器上，这三遍说明把对话本身挤到了很薄的一条。

## 二、这一轮改了什么（只动两处渲染，不动逻辑）

1. 「对话方式」那一行：**平台对话**下不再重复列「长上下文 · 联网搜索 · 读链接 · 思考模式」——
   下面那排开关就是它们；预设那一侧没有开关，说明保留。
2. 空状态四条并成两条：流式与计费一条，附件与链接一条（联网搜索没接通时照实说）。
3. 输入框下的提示只留 `Enter 发送 · Shift + Enter 换行`；附件上限（5 个 / 图片 2 张 / 8 MB）
   挪进「附件」按钮的 `title`，信息没丢，只是不再占一行字。

## 三、对话框直接生图 / 生视频：接法先对齐，不半截上线

先说结论：**现在接不通**，而且不是配置问题，是架构问题。查清了这四件事：

1. 对话有**两个入口**：「平台对话」走 `server/routes/chat.mjs` + `QuickChat.tsx`；
   「对话预设」走 `server/routes/agents.mjs` + `server/agentChat.mjs`。两条链路各自独立。
2. `server/agents.mjs` 里的 `AGENT_TOOLS` 早就声明了 `image-gen`，但 `state: 'planned'`——
   注释写得很直白：只作能力声明展示，**不会执行**，也不假装执行。
3. 现在的「工具」其实都是**请求前读上下文**（模板库、工作流、网页、附件），
   模型没有任何决定权：`chatcall.mjs` 的 `chatCompletion` 没有把 `tools` / `tool_calls` 透出来，
   `callTextModel` 只回 `text`。所以「DeepSeek 自己决定去生图」这条路今天物理上不存在。
4. 生图/生视频的管线是现成的（`server/routes/media-gen.mjs` 的 `runImage` / `runVideo`：
   先扣费、失败全额退、任务落 `data/media/tasks`、结果留在「最近生成」）。真正缺的只是
   **谁来决定调用它**，以及**它怎么回到对话里**。

两条接法，各有代价：

| 接法 | 怎么做 | 代价 / 风险 |
| --- | --- | --- |
| A. 真函数调用 | 把 `tools` 透到上游；模型回 `tool_calls` 就执行生成、把结果回灌再让它写正文 | 要改 `chatcall` / `llm` 三处；**上游 deepseek-flash 到底认不认 tools 没验过**，验一次要真调文本（约 ¥0.05）；模型不稳时会「该生成不生成」 |
| B. 明确触发词 | 消息里出现「生成一张图 / 画一张 / 出一段视频」时，服务端直接走现成管线，模型只负责写正文与提示词 | 100% 可本地验证、0 费用；但「聪明的判断」少了，靠明确的说法 |

我的建议：**B 先上**（本周就能真跑通、可验收），把 A 当作它后面的增强——
A 要花一次真实文本调用确认上游支持函数调用，这一步得你点头。
