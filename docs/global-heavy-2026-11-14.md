# 全站重活上限：跨账号的并发也管住（v0.9.70，2026-11-14）

## 一、结论先行

- **问题**：上一版（v0.9.69）只做了「这台机器还剩多少内存」和**按账号**的并发。它管不住最常见的那种超载：**两个账号各开两条重活**——按账号看每个人都合规，合起来 4 条同时跑，2 核 / 1.86 GB 直接顶穿。进程被 OOM 杀掉时所有人的会话一起断，正在跑的任务只能靠重启后的中断恢复退款。
- **做法**：在同一个闸门里再加一层**全站（不分账号）重活条数上限**。数字来自已有的进程内并发计数（`gate.mjs`），判定仍然只写在一处（`waterline.mjs`）。名额满了就在**扣费之前**返回 503 `SERVER_BUSY`，这一单不扣积分、不落任务、不调上游。修完名额立刻还回来。
- **验收**：默认上限 **3 条**（`VQ_GLOBAL_HEAVY`，0 = 不限）。生产已上（v0.9.70），后台「系统 → 运行水位」多一行「全站重活 N 条在跑 / 上限 3 条」。跨账号的拒绝用一次性实例 + 慢假上游真跑了一遍：A 的画布在跑时 B 的复刻 → **503 `SERVER_BUSY`**，B 余额 **100 → 100**、job 表 **0 → 0**；A 跑完后 B 立刻 **200** 接单并正常扣费。测试 **616/616**（+7）。
- 顺带修了一个**测量错误**：上一轮数 5xx 用的是服务器上的 `grep`，模式 `,s.:5` 一条都匹配不到（真实字段是 `,"s":500`），所以「0 个 5xx」其实什么都没数到。本轮加了 `scripts/log-status.mjs`，解析 JSON 后按状态码统计（见第五节）。

## 二、为什么还需要全站这一层

v0.9.69 的并发上限是**每账号每类型**的：复刻 2、评审 1、画布运行 1。它对「一个人连点」有效，对下面这种情况无效：

| 谁 | 在跑 | 按账号看 | 合起来 |
| --- | --- | --- | --- |
| 账号 A | 2 条复刻 | 合规（上限 2） | 4 条重活同时跑 |
| 账号 B | 2 条复刻 | 合规（上限 2） | 2 核 / 1.86 GB 顶不住 |

真正要守的约束是「**这台机器同时能扛几条**」，不是「每个人能开几条」。所以这一层的计数必须跨账号。

## 三、做了什么

| 环节 | 做法 | 在哪 |
| --- | --- | --- |
| 数 | 复用并发闸门已有的进程内计数，只读地按 kind 汇总（`activeFor`） | `server/gate.mjs` |
| 限 | 全站重活上限默认 **3 条**；`VQ_GLOBAL_HEAVY=0` 关闭这一层；水位偏紧时**再折到 2 条** | `server/waterline.mjs` `globalHeavyCap()`、`server/config.mjs` |
| 拒 | 名额满 → 扣费前 **503 `SERVER_BUSY`**，带 `active` / `limit` / `retryAfterSec: 60`；提示写清「没有扣积分」 | `admit()`（三处付费入口共用） |
| 还 | 名额在任务真正结束时归还，走的是**原来就有的** `release()` / `onSettled` / `finally` 路径——没有新增一条「忘记释放就永久卡死」的面 | `index.mjs` / `routes/review.mjs` / `routes/flows.mjs` |
| 可见 | 后台「系统 → 运行水位」新增「全站重活」一行 + 排满时一行红字；判定口径里写出上限 | `src/pages/admin/WaterlineCard.tsx` |
| 只读 | 上限只由部署环境变量决定，后台没有写入入口 | `GET /api/admin/waterline` |

### 为什么不会「两个请求同时挤进最后一个空位」

`admit()` 里「看计数 → 判断 → 放行」，和紧接着 `enter()` 的「计数 +1」，**在同一段同步代码里**，中间没有 `await`。Node 单线程下不会在两者之间切走，所以不存在两个请求都看见「还差一个」然后一起进去的情况。这是刻意保持的写法：把 `admit` 与 `enter` 之间的代码改成异步（例如中间查一次数据库）就会引入超额窗口。

### 计数是进程内的

和按账号的并发闸门同一口径：**单机部署足够**，进程重启时在跑的任务本来也就没了（靠 v0.9.48 的中断恢复退款收尾）。多机 / 多进程部署时这层要换成共享计数（Redis 之类），那时才需要。

## 五、跨账号拒绝怎么验的（一次性实例，零扣费）

生产没有第二个账号在跑重活，所以在最短路径上复刻真场景：一次性实例 + **本地假上游故意慢 20 秒**，让账号 A 的画布运行真的挂在「在跑」；这时账号 B 请求一键复刻。

| 时刻 | 实测 |
| --- | --- |
| A 在跑时 `GET /api/admin/waterline` | `heavy: { active: 1, byKind: { flow_run: 1 }, limit: 1, full: true }`，`level: ok`（内存没到红线，纯粹是名额满） |
| B 的 `POST /api/replicate` | **503 `SERVER_BUSY`**：`{"active":1,"limit":1,"retryAfterSec":60}`，提示「服务器正在同时跑 1 条重活（上限 1 条），这条任务没有开始（没有扣积分）。等一分钟再试。」 |
| B 的余额 / 任务 | 积分 **100 → 100**；job 表 **0 → 0**（不落任务、不碰来源链接、不调上游） |
| A 跑完后 | `heavy.active 0`、`full: false`；B 再发复刻 → **200**、`job_aacf870b`、扣 **10** 积分（与单价一致） |

后台那一屏的排满态也截了图（本机一次性实例，`VQ_GLOBAL_HEAVY=1`）：见文末第三张。

## 六、口径纠正：5xx 不能用正则数

上一轮（v0.9.69）在服务器上这样数 5xx：

`~bash
journalctl -u visionqa --since '20 min ago' -o cat | grep -c -e ,s.:5
`~

两个问题：

1. **匹配不到**：真实字段是 `,"s":500`（逗号 → 引号 → s）。模式 `,s.:5` 要求逗号后面直接是 s，所以命中 0 行——**0 是「没数到」，不是「没有」**。
2. 去掉逗号写成 `s.:5` 又会**误命中耗时字段** `"ms":52`，把正常的慢请求数成 5xx。

正确做法是解析 JSON 再数。本轮加了 [`scripts/log-status.mjs`](../scripts/log-status.mjs)：

`~bash
node scripts/log-status.mjs .tmp-qa/vq-log-36h.txt --since 2026-11-13T18:20:00Z
# 访问记录 186 条
#   200: 186
# 5xx: 0
`~

补数的完整 36 小时窗口（7933 条访问记录）真实分布：

| 状态 | 条数 | 说明 |
| --- | --- | --- |
| 200 / 201 / 202 / 204 | 7778 / 40 / 12 / 2 | 正常 |
| 400 / 401 / 404 / 405 | 8 / 55 / 23 / 3 | 401 多为未登录轮询 `/api/auth/me`，404 是旧分享链接与已删除对象 |
| 429 | 1 | 并发或额度闸门（预期内） |
| 500 | 5 | **全在 11-12**：一次 42 秒的评审超时、四条同一张作品的路由报错 |
| 502 / 503 | 2 / 4 | 出图 502（上游 SeeAPI 拒绝，见 v0.9.56 的幂等键透传）与 v0.9.70 之前的网关 503 |
| 5xx 合计 | **11** | 全部早于 v0.9.69 的部署时间；v0.9.69 / v0.9.70 部署之后 **0 条** |

这条纠正的意义不是数字好看——是**几周来「部署后 0 个 5xx」这个结论一直是空数**。以后再报这个数，用脚本，不用正则。

## 七、边界

- **不是 worker 隔离**：重活仍在同一个 Node 进程里，靠「少放几条进来」而不是「分到另一台机器」。真要开生成（出图/出视频）还是得独立机器。
- 上限是**经验值**（3 条），没做压测：B2 的「10 个并发不出 OOM」仍未做。
- 计数是**进程内**的：多机部署要换成共享计数，这一层才算全局。
- 只拦三个付费重活（复刻 / 评审 / 画布运行）；检索、对话、上传不跟着拦。
- 名额满**不**单独进告警：它是「忙」，不是故障；真到内存红线才记一条 `memory` 告警（5 分钟节流）。

## 九、回滚

- 只想**关掉这一层**、保留水位：部署环境加 `VQ_GLOBAL_HEAVY=0`（后台那一行会显示「不限」）。
- 整条守卫都关掉（只量不拦）：`VQ_WATER_GUARD=0`。
- 回上一版：`bash /opt/visionqa/ops/rollback.sh --to <release 序号>`。
