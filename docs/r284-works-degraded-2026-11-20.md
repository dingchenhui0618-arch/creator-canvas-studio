# 作品流：「读不到」不许画成「没有」（r284 / v0.9.266）

## 为什么这一条算上线前缺的东西

作品流把三处产物收成一条流：快捷创作的图与视频、工作流的运行记录、无限画布（另一个应用，跑在 6677/5312）。
三处各读各的，而以前**任何一处读失败，界面都画成「这一类还没有作品」**：

- 无限画布服务没连上 → 这一栏 0 条 + 一句「在无限画布上出过图或视频，就会进这里；只摆过素材、没出过东西的画布不算。」
- 于是一个真在画布里出过 30 张图的人，打开作品流看到的是「你从来没在画布里出过东西」。
- 顶部还写着「共 N 条」——漏了一处来源的数字被当成总数。

这与项目自己的口径相反（空 / 坏必须分开，见 `docs/empty-vs-error-states-2026-11-19.md`）。
画布是第三方应用，挂的机率不低；偏偏它挂了的时候最难分辨「坏了」还是「没做过」。

## 改法（四条口径，服务端给、界面照画）

| 问题 | 结论 |
| --- | --- |
| 服务端怎么表达 | 三个来源各自回 `{ items, error }`，合成一页时带 `degraded: { media?, runs?, canvas? }`，值就是给用户看的那一句话 |
| 数字怎么写 | 读不到的那一栏写「—」而不是 0；「全部」也不写死数（漏了一处的不是总数），并说明「有一处来源没读到」 |
| 空状态怎么写 | 分三种：**没读到**（给「重新读取」）/ 这一类真没有（切回全部）/ 一条都没有 |
| 一处坏会不会拖垮整条流 | 不会。三处并行读，各自兜住自己的失败；以前 `listRuns` 抛错会把整个 `/api/works` 变成 500 |

顺带修掉同一处的一个量词谎话：快捷创作的作品只扫最近 400 份元数据，但以前按**目录顺序**取前 400 个名字——
文件系统不按时间排，真正「最近」的那张可能压根没被扫到。现在超过上限时先按 mtime 排序再取，没超就不多做 400 次 stat。

## 改了哪几处

- `server/works-feed.mjs`：`mediaItems` / `runItems` / `canvasItems` 各自回 `{ items, error }`；新增 `newestNames`（按 mtime 取最新 N 个）与 `cleanDegraded`；`mergeWorks` 把 `degraded` 原样带回；`listWorks` 三处并行、只把失败翻成一句话。
  - 目录不存在（新账号还什么都没生成过）算「还没有」，不算「读不到」——那正是新账号该看到的样子。
- `src/api/works.ts`：`WorksSource` / `WorksDegraded` / `WorksPage.degraded`。
- `src/domain/works-view.ts`：`worksKindSource` / `worksKindGap` / `worksSourceGaps` / `worksChipCount` / `worksEmptyKind`——判断都在这里，界面不另算一遍。
- `src/components/WorksWall.tsx`：胶囊数字、缺口说明（一枚「重新读取」）、空状态三分支、`总数` 措辞。
- `src/styles/works.css`：`.works-gap`（12px 内边距、13px、warn 图标）、`.works-gap-retry`（桌面 24px / ≤560 抬到 32px）、`.works-empty-actions`。

## 实测（临时实例 + 假无限画布，0 次真实上游调用、0 费用）

一个账号、一张已生成的图（9:16，用仓库里那张真实抽帧当成品）、一块认领给它的画布（6 个节点，其中 1 张出好的图）。

| 状态 | 实测 |
| --- | --- |
| 画布服务连不上 | 胶囊：`全部 —`、`无限画布 —`（不是 0，也不压暗）；顶部「读到 1 条」；说明条「这次没读到：无限画布暂时连不上：作品、模板、评审、交付都不受影响；过一会儿刷新再试。这不是「那里没有作品」——别的来源照常显示，读不到的那一部分数字写「—」。」+「重新读取」 |
| 停在「无限画布」这一栏（旧行为是「无限画布这一类还没有作品」） | 标题「无限画布这次没读到」，正文说清这不是「这里没有作品」，并给「重新读取」+「看全部 1 条」 |
| 390（按 390 重新载入） | 那枚「重新读取」78×32、13px，页面 `scrollWidth = clientWidth = 390` |
| 画布服务起来后点「重新读取」 | 说明条自己消失；胶囊变成 `全部 3` / `图片 2` / `无限画布 1`；卡片 3 张（画布里那张图、快捷创作那张图、画布本身）；顶部「共 3 条」 |

## 边界（说清楚，不假装）

- 只有画布这一路是「外部应用会挂」；快捷创作与工作流的读取失败（盘坏、权限）同样会走这套提示，但那属于本机故障，正常见不到。
- 「重新读取」是**整页重取**（当前筛选与关键词不变），不是只补那一处来源；预算有限所以没做「只重取画布」。
- 三处来源各自有扫描上限（媒体 400、运行 50、画布前 12 块），作品流仍然不是全库检索；搜不到的说明照旧写在搜索结果那一段。
- 画布服务真挂掉时，进画布这条路（`#/board/<id>`）仍然会失败，作品流只负责「不把失败说成没有」，不负责替画布重试。
## 顺手修掉的另一个「结果会丢」的坑（同一轮）

跑门禁时 media-gen 有一条连红三次：`任务一直是 processing，后台没有收敛`。
翻测试留下的日志抓到真凶：

```
{"t":"media.generate.error","error":"EPERM: operation not permitted, rename '…/mgen_x.json.tmp' -> '…/mgen_x.json'"}
```

任务元数据是「写 .tmp 再 rename 覆盖」。这个 rename 在 Windows 上会被**正被打开的那个目标文件**挡住（EPERM）；
而最近生成 / 作品流每 2.5 秒就轮询一次同一个任务文件——两边撞上，这一次终态就写不进去：
任务永远停在「进行中」，用户已经付过的积分也拿不到结果（结果与退款都写在这次写里）。

改法：新增 `server/atomic-write.mjs`——`writeFileAtomic` 写临时文件后走 `renameWithRetry`，
只对**暂时性**错误码（EPERM / EBUSY / EACCES / EAGAIN）重试，最多 6 次、逐次多等一点；
别的错误（路径不存在、盘满）立刻抛，临时文件删掉，不装成写成功。生图 / 生视频的任务元数据改走它。

补完这条，media-gen 从 20/21（连红三次）变成 21/21。同样的写法在服务端还有约 40 处
（作品、积分、模板、评审……），下一轮再统一迁到这个 helper 上——本轮只动真正会丢钱的那一处。
