# 平台 Key 路由与故障回退

> 目标项②「建立可扩展的平台 Key 接入与路由（多供应商 / 多 Key / 权重与故障回退），管理员可自由增删改」
> 的落地说明与线上证据。最后更新：2026-11-11（第二十九批）。

## 一、为什么要有这一层

接入前，模型凭证写死在环境变量里：换供应商要改配置发版，一个 Key 额度用完就是整站不可用，
管理员在后台看不到「刚才那次调用走的是哪把、为什么、成没成」。现在的做法是：

- 凭证只落在服务端加密文件里（AES-256-GCM），列表接口只回脱敏值，日志与前端永远拿不到明文；
- 每把 Key 声明能力、模型白名单、优先级、权重，管理员在后台随时增删改，改完立即生效、不用重启；
- 每次真实调用都落一条路由记录（走了哪把、判定理由、耗时、成没成），日志落盘，发版重启不清空。

## 二、选 Key 的规则

| 步骤 | 规则 |
| --- | --- |
| 1. 能力 | 调用方声明 `text / vision / image / video / judge`，只在这类 Key 里挑；别名（chat/llm/multimodal/jev/typesafe…）会归一 |
| 2. 模型 | Key 声明了模型白名单时，只接受名单里的模型；名单为空表示通用 Key |
| 3. 停用 / 冷却 | `enabled=false` 与冷却中的 Key 直接跳过，冷却 60 秒（连续失败 3 次触发） |
| 4. 优先级 | 数值小的先试（P0 最先，P100 其次） |
| 5. 权重 | 同优先级里按权重随机；后台预演显示的百分比与真实抽取共用同一套判定 |
| 6. 空池 | 池里没有任何可用 Key 时回落到环境变量旧凭证，路由日志标 `env`；环境变量也没配则明确报「未配置模型凭证」 |

## 三、故障回退（本轮补齐的部分）

之前只有判断层（judge）与出图 / 出视频走「候选列表 + 逐把重试」，**文本与视觉只取一把**：
首选 Key 欠费或凭证失效，整条模型链就算失败，后面明明可用的 Key 没机会上场。

现在 `chatCompletion` 统一改成：

1. 按上面的规则拿到候选列表（默认最多 3 把，按优先级 + 权重排序，不放回）；
2. 第 1 把失败就换第 2 把，每次真实请求各记一条路由记录，带 `attempt` 序号；
3. 后台「换 Key 成功」= `attempt > 1 且成功` 的记录数，能直接看出「这次是第几把接住的」；
4. 以下两类**不换把**：
   - **输出被 max_tokens 截断**：这是模型与参数的问题，换同模型的另一把只会再截断一次，白花钱；
     交给上层的模型降级链去换模型；
   - **上游不认 `response_format`（HTTP 400）**：同一把 Key 去掉 json 模式原地重试一次，且不计失败次数。

判断层与出图 / 出视频原本就有回退，规则一致；本轮只是让文本与视觉跟上。

## 四、线上演练（生产 139.196.123.28，2026-11-11 16:15）

做法：临时往池里插一把**故意写错的 Key**（优先级 P0，比真 Key 的 P100 更靠前），
用管理员账号发起一次真实对话，随后立刻删除演练 Key。

| 步骤 | 线上结果 |
| --- | --- |
| 建演练 Key | `k_b034e3655f76`「演练·故意失效的 Key」，P0 / W10，能力 text，模型 `deepseek-flash` |
| 调用前预演 | 「现在调用会用「演练·故意失效的 Key」（优先级 P0）」 |
| 第 1 次尝试 | `attempt 1` · 演练 Key · **凭证无效（HTTP 401）· 131 ms** |
| 第 2 次尝试 | `attempt 2` · DeepSeek 官方（原环境变量）· **成功 · 803 ms** |
| 调用结果 | 智能体正常回「收到」，模型 `deepseek-flash`，接口 200（前端无感） |
| 汇总计数 | 「换 Key 成功」由 1 变 **2**（一次对话里两段文本调用各回退一次） |
| 删除演练 Key | 200，池内恢复 2 把；预演回到「会用 DeepSeek 官方（优先级 P100）」 |

截图：`docs/screenshot-key-failover-2026-11-11.png`（后台「模型 Key → 最近路由」）。

结论：**故障回退在生产真的生效**，不是只有代码和单测；且整次演练没有产生费用（失败的是无效凭证，
只有一次成功的正常对话）。

## 六、尚未验证 / 待办

- **真实多供应商同时可用**没测过：目前 text 只有 DeepSeek 一把能真调用，SeeAPI 只声明出图出视频；
  回退演练用的是「故意失效的 Key」。要证明「A 家挂了自动走 B 家」，得再买一家文本额度。
- **权重分布只做过本地 2000 次抽样**（25.3% / 74.7%），没有在生产长时间统计真实命中比例。
- 冷却只存在进程内存里，重启即清零（设计如此：避免重启后把刚恢复的 Key 继续挡住）；
  后台「冷却中」的秒数因此每次发版会重置。
- 同名 Key 在「按 Key 汇总」里会带末四位区分（如「演练·故意失效的 Key（5f76）」），
  但历史记录里旧数据仍按 Key id 分开统计。

## 七、后台怎么改（管理页操作）

后台 → 模型 Key（`/#/admin/keys`）：

- 顶部表单新建：名称 / 渠道 / 接口地址 / API Key / 模型 / 能力 / 优先级 / 权重；
- 行尾「编辑」在那一行下面展开编辑面板，可改名称、渠道、接口地址、模型、能力、优先级、权重；
  **API Key 留空表示不换**，粘贴新的即轮换凭证（列表接口拿不到明文，编辑框永远不回填旧 Key）；
- 「删除」需要二次确认；「测试」会真打一次（出图 / 视频只验凭证，判断能力额外跑一次判断自检）。

改完即生效：下一次模型调用就按新的优先级与权重选 Key，不需要重启进程，也不丢调用统计与路由记录。
