# 数据文件读不出来时不再当空库（r265 / v0.9.247）

日期：2026-11-19　版本：0.9.247

## 一、为什么查到这里

模板库顶部有两格数字：**模板总数**、**作品在用**。上线前巡检时出现过「模板总数 0、作品在用 1」这种自相矛盾的组合——
0 条模板，却有 1 条作品在用模板。顺着这个矛盾往下看，发现两件事：

1. **作品指着的模板可能已经不在库里**（删到回收站 / 彻底删除 / 属于别的账号）。作品还在，模板没了，
   两格数字各算各的，于是互相打架。
2. 更糟的是那些存储的读法：模板库、作品库、工作流与运行记录都是「整份读、改一条、整份写回」，
   而读失败一律 `catch { cache = [] }`。也就是说，**文件只要有一次读不出来（JSON 写坏、权限不对、
   盘上留了半个文件），页面显示的就是「一条都没有」**；用户随手新建一条，整份内容就被这一条覆盖掉了——
   数据是静默丢的，没有任何提示。巡检时本地复现过一次（文件损坏时页面正好就是「0 条 / 作品在用 1」），
   这也是上面那个矛盾会出现的第二种原因。

## 二、改了什么

| 位置 | 以前 | 现在 |
| --- | --- | --- |
| 读 `templates.json` / `projects.json` / `flows.json` / `runs.json` | 读失败一律当空数组 | 只有文件不存在（ENOENT）算空库；读不动、不是合法 JSON、顶层不是数组 → 抛 `STORE_UNREADABLE` |
| 写回 | 不管读没读到都整份写回 | 这一次读失败过就拒绝写回，一个字节都不动 |
| 模板库页面 | 读失败时照样显示「模板总数 0」，下面还写「模板库还是空的」 | 不显示那几格 0；只写「模板库现在读不出来」+ 具体原因 + 「再试一次」 |
| 服务启动 | 运行记录读不出来 → 整站起不来 | 跳过「恢复上次没跑完的运行」这一步、记一行日志，站点照常启动，用户侧读运行记录时才看到明确报错 |
| 文件修好以后 | 要重启才恢复（如果此前被写坏） | 下一次请求就会重新读，自动恢复，失败标记同时清掉 |

具体实现：新增 `server/json-store.mjs`（`readStoreArray` / `storeUnreadable`），三个存储模块的
`loadAll` 改用它，并在 `persist` 里加一道「读失败过就不许写」的闸。用户侧文案固定为
「模板库数据读不出来（文件可能损坏）：这一次没有改动任何内容，请联系管理员」——
不带文件路径、不带堆栈，排障细节留在服务端日志（`request.refused` / 5xx 那一路）。

## 三、两格数字不再打架

`server/template-usage.mjs` 新增 `usageTotals(byTemplate, liveIds)`：

- `projectTotal`：只数**库里看得见、又不在回收站**的模板名下的作品；
- `orphanTotal`：作品还指着已经删掉 / 回收站里 / 看不见的模板，单独算一个数。

`GET /api/templates` 多回一个 `orphanTotal`。模板库页面在它 > 0 时多一行：

> 另有 1 条作品用的模板已经删除或还在回收站里，没算进上面「作品在用」　〔打开回收站〕

不把那条作品偷偷漏掉，也不用「作品在用」去暗示一条已经不存在的模板。

  修好文件自动恢复）、`test/store-missing.test.mjs` 3 条（没有文件仍算空库、新建第一条照常落盘）、
  `test/template-usage.test.mjs` 新增 1 条（orphan 计数）。
- 全量 **1740/1740** 通过；`tsc -b` 干净；lint 0 error / 25 warning（632 文件）；密钥扫描 1007 文件无命中。

## 五、边界

- 只改了模板、作品、工作流、运行记录这四份数据。**智能体、评审、告警、反馈、访问日志等模块还是老写法**
  （读失败当空库），它们的危害小一些（丢了不至于把用户作品覆盖掉），但同一类问题仍然存在，下一轮再收。
- 没有做「自动从备份恢复」，也没有人工修复工具；文件真坏了要管理员从备份恢复。
- 文件损坏只在本地临时实例上复现过（生产四份数据都是好的），没有在生产上人为造坏。
- 两格数字的口径是「当前账号看得见的模板」：管理员看 26 条时若其中一条在回收站里，管理员看到的是 25 + orphan 1。
