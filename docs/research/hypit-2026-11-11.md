# Hypit 能否融入 VisionQA「爆款视频复刻」链路

日期：2026-11-11 · 状态：**只读调研，未改任何代码** · 对象：`hypit-ai/hypit` @ `main` commit `3e49a97`（2026-11-09，v0.3.2）+ npm `@hypit/hypit@0.3.1`

结论：**逻辑能融，但不能整体搬。** 值得拿过来的是「把视频表达编译成一张有类型、可规划、可重跑的执行图」这件方法论，以及它配套的**语义时间轴（词/句/瞬间锚点）**与**显式复用**；不值得拿的是它那批 40–60 KB 级的专有视觉组件和桌面 Studio。

---

## 一、结论先行

1. **它没有"自动拆解器"。** 全仓不存在 video → SVML 的转换器：拆解由 agent 读 `skills/hypit/SKILL.md` 与 `skills/hypit/references/creation/reference-video.md`，用 `hypit transcribe` / `hypit media tile --transcript` 取证后**手写** SVML。VisionQA 的 `server/vision.mjs: analyzeFrames()`（一次调用出结构化模板）在"自动化拆解"这件事上反而更产品化。→ **模板库与分镜这一层要借它的数据模型，不要指望它的流程。**

2. **它的强项正好压在 VisionQA 现在的三块短板上**：
   - **（a）时间锚在词上，不在秒上**：`<script>` 产出 CaptionDocument（Display Word / Alignment Unit / Cue），`narrative-temporal` 把 `@{selection}` / `@{moment!}` 投影成绝对窗口。VisionQA 现在是"均匀抽帧 + 模型猜 startSec/endSec"，同一句台词改一个字，整条分镜的时间全废。
   - **（b）显式复用让"100 个变体"不重复烧钱**：`.svrun` 里 `<build-record>` + `<satisfy>` 把上一次 Build 的某个 Output 直接钉成候选。VisionQA 的 `jobs.mjs` 每次重跑都从头再来。
   - **（c）付费前先能看清单**：`hypit plan` / `hypit pricing` 只读不执行，`--json` 是稳定机器视图。VisionQA 的积分扣费（`credits.mjs`）目前拿不到上游真实单价。

3. **许可证是比技术更硬的门槛。** `LICENSE` 1a/1b 明确：**多租户服务**与**商业再分发**都必须先拿到书面的商业许可；1c 还禁止去掉 CLI / 运行报告 / manifest 里的 Hypit 名称与 LOGO。VisionQA 是带账号、计费、模板库的**多用户工作台** —— 一旦对外提供即构成"多租户"，**必须谈许可**；纯内部单租户（自己公司给客户做片）则被明确允许。

4. **推荐路线：P0 借壳 + P1 借语义 + 不搬重资产。** P0 用 `hypit --json` 当执行后端（4–7 人日）；P1 把语义锚点与复用语义移植进 VisionQA 自己的数据模型（15–25 人日）；`caption-fine` / `ranking` / `studio` 这类 30–60 KB 单文件组件**不搬**（见第六节 6.5）。

5. **给 lead 的一句话**：这事值得做，但**先别写整合代码** —— 先批一周做 P0 PoC（同一条 15 秒片子，用 VisionQA 现有链路 vs 用 `hypit build` 各出一版，比时间、比钱、比重跑的一致性），同时让法务看 LICENSE 1a 的"tenant = workspace"怎么套到我们的账号体系上。

## 三、SVML 是什么

一句话：**SVML 不是"视频脚本语言"，是把视频制作编译成"带类型的算子图"的标记语言外壳。** 语法解析器本身不认识任何视频概念（`packages/markup/src/syntax.ts: discoverMarkup() / parseStructuredElement()` 只是通用结构化标记），视频语义全部由**包注册的 Surface** 提供。

### 3.1 三种源，一条指令

三种文件都以处理指令开头，指令决定用哪个前端（frontend）解析：

| 文件 | 处理指令 | 根元素 | 作用 | 解析入口 |
| --- | --- | --- | --- | --- |
| `*.svml` | `<?svml using="@hypit/markup@1"?>` | `<svml>` | Author Source：整片编排 | `markup/frontend.ts: createMarkupAuthorFrontend()` |
| `*.svs` | `<?svml using="@hypit/recipe@1"?>` | `<sheet version="1">` | Recipe：样式/参数包（字幕描边、板子配色、镜头稳定性…） | `recipe/parser.ts` |
| `*.svrun` | `<?svml using="@hypit/markup/run@1"?>` | `<svrun version="1">` | Run Source：选目标、选候选、钉复用 | `markup/src/run/syntax.ts` |

### 3.2 一个真实例子（`examples/ranking-football/reference.svml`，356 行）

它把一条 20 秒的足球排名整活视频写成了一张图，顺序是：

```svml
<import from="@hypit/script@1"/>                  ← 脚本面
<import as="gpt" from="@hypit/gpt-image@1"/>      ← 图像模型
<import as="seedance" from="@hypit/seedance@1"/>  ← 视频模型
<import as="whisperx" from="@hypit/whisperx@1"/>  ← 词级对齐
<import as="semantic" from="@hypit/narrative-temporal@1"/>  ← 语义→绝对时间
<import as="caption-fine" from="@hypit/caption-fine@1"/>

<script id="story">  <ronaldo> <HOST>Ronaldo is <D | Dee> tier. || Bro has @{hair-gel} more …</ronaldo> </script>
<gpt:Image id="presenter" prompt={presenter-prompt} aspect-ratio="9:16" resolution="2K"/>
<seedance:ReferenceVideo id="ronaldo-take" model="mini" prompt={ronaldo-prompt} duration="10">
  <seedance:Reference image={presenter.image} person-reference="true"/>
  <seedance:Reference audio={presenter-voice.reference}/>
</seedance:ReferenceVideo>
<whisperx:Alignment id="ronaldo-semantic" narrative={story} segment={story.segment.ronaldo} …/>
<semantic:Projection id="story-time" narrative={story} timeline={speech.timeline}> … </semantic:Projection>
<semantic:Window id="selection-hair-gel" projection={story-time} during={story.selection.hair-gel}/>
<visual:Clip id="hair-gel" image={broll-hair-gel.image} during={selection-hair-gel} z="40" motion={broll-left}/>
<caption-fine:Caption id="captions" document={story.caption} timing={caption-timing} …/>
<film:Film id="main" canvas={vertical.canvas} timeline={speech.timeline} appearance={recipes.film.vertical}>
  <film:Track source={picture.visual}/> <film:Track source={mix.audio}/>
  <film:Track source={football-tiers.visual}/> <film:Track source={captions.visual}/>
</film:Film>
<html:Video id="final" composition={main.composition} timeline={speech.timeline}/>
```

**这一段就说明了它的世界观**：脚本（词）→ 生成素材（图/声/视频）→ 对齐拿到词的时间 → 投影成窗口 → 画面/板子/字幕各自消费窗口 → Film 合成 → html:Video 出片。**没有任何地方写"第 3.2 秒切镜"**，切点全部挂在词上。

### 3.3 `<script>` 的语义密度（这是最值得抄的部分）

依据 `docs/quickstart/script.md` 与 `packages/script/src/parser.ts: parseScript()`：

| 概念 | 语法 | 语义 |
| --- | --- | --- |
| Segment | `<hook> … </hook>` | 口播段落，名字即 id，不可嵌套 |
| Role Cue | `<HOST>` 起头、无闭合标签 | 谁在说；不是角色实体，不选音色 |
| Dual Text | `<SVML \| semantic video markup language>` | 左侧上屏、右侧念白，**N:M 对齐单元**（不是 1:1 替换） |
| Cue 分隔 | `\|\|` | 切字幕条 |
| Selection | `@{problem} … @{/problem}` | 命名的**时间区间**（不是帧段） |
| Moment | `@{ranking!}` | 命名的**时间点** |
| 吸收方向 | `@{~id}` / `@{/id~}` | 边界贴左/贴右 |

编译产物是一个 **CaptionDocument**（Display Word / Alignment Unit / Cue，不带秒也不带帧），再由 `narrative-caption:Timing` 结合对齐结果算出逐词 cue 时间。中文按**字**切词（`script.md` 明确写了"Han/Hiragana/Katakana 按字符级 lexical unit 切分"），所以中文不会变成一个大词。

## 四、它怎么把一条视频拆成可执行工作流

### 4.1 拆解这一侧：全是文档 + agent，没有分析器

依据 `skills/hypit/SKILL.md`（导演/制片人设）、`references/creation/reference-video.md`（读片方法）、`references/creation/project-files.md`（文件即记忆）：

| 阶段 | 产出 | 谁产 |
| --- | --- | --- |
| 看片取证 | `references/<ref>/transcript.json`（`hypit transcribe`）、`evidence/*.jpg`（`hypit media tile/tiles --transcript`，带词标注的帧网格） | 工具 |
| 理解 | `ANALYSIS.md`（整片为什么成立）+ `TIMELINE.md`（按源时间的细读，标"这个动效对观众做了什么"） | **agent 手写** |
| 目标 | `BRIEF.md`（用户要什么、预算边界）+ `TREATMENT.md`（导演自己的答案） | **agent 手写** |
| 实施 | `authors/*.svml`、`recipes/*.svs`、`runs/*.svrun` | **agent 手写** |
| 交接 | `PROGRESS.md`（当前问题、下一步、Build id） | **agent 手写** |

**这是本次调研最重要的一条判断**：Hypit 的"复刻能力" = **一套很讲究的制作方法论文本 + 一个能把方法论落成图并执行的编译器**。前者不可直接搬（是它们的品味资产，也是 LICENSE 之外没法复制的部分），后者可以借。

### 4.2 执行这一侧：五段式编译 + 事件溯源执行

```
.svml/.svs/.svrun
   │  markup/src/syntax.ts: discoverMarkup / parseStructuredElement      （通用标记 → 结构化树）
   │  <package>/manifest.ts: markupSurfaces                             （元素 → records/components/fragments）
   ▼  compiler/src/source.ts: compileSourceClosure → hygienizeSource    （import 闭包 + 去重 + provenance）
   │  kernel/src/link.ts: link + resolveProducer                        （拼成带类型的 Program）
   │  author/src/author.ts: elaborateAuthorGraph                        （组件实例化 → 算子图）
   │  author/src/fragment.ts: sealGraphFragment                         （复用的最小单元）
   │  compiler/src/run.ts: class RunCompiler                            （.svrun → RunGraph：targets/candidates/satisfy）
   ▼  kernel/src/plan.ts: planBuild / verifyBuildPlan                   （裁剪出**只到目标**的有限 plan）
   │  kernel/src/machine.ts: class BuildMachine + reducer.ts            （Definition + Facts 事件溯源）
   ▼  executor/src/executor.ts: class Executor                          （跑 step / 发 need / 记 fact）
      endpoint/src/index.ts: defineEndpoint                            （immediate 或 async: submit→poll→collect）
```

关键设计（值得抄的地方）：

| 设计 | 证据 | 为什么重要 |
| --- | --- | --- |
| **算子只有两种结果：output 或 need** | `protocol/build.ts: OperationResult` | 纯计算与外呼在类型上分开，plan 才能只统计"要花钱的 need" |
| **ProducerStep 必须只有一个原子结果** | `kernel/src/plan.ts: STEP_RESULT_NORMAL_FORM` | 保证图可拓扑排序、可增量重算 |
| **plan 必须无环且每个 step 都通向目标** | `plan.ts: assertAcyclic() / assertAllStepsReachGoal()` | 不会静默跑一堆没人要的边 |
| **复用是显式的，没有隐式缓存** | `docs/quickstart/run.md`："Hypit has no implicit cache"；`build-record` + `satisfy` | 生成是非确定性的，自动缓存会让"重跑结果不一样"变成 bug 而不是 feature |
| **每次 build 都给新 id** | `packages/cli/src/main.ts: createPublicBuildId()` | 结果可寻址；`hypit history <output>` 能反查 |
| **失败即失败，不自动整链重试** | `docs/guide/runtime.md` + `status` | 已经花钱生成的 Output 仍在 Result 里，可用 `build-record` 捞回来重跑下游 |

### 4.3 渲染管线（本地、可离线）

`packages/html-video/src/fragment.ts: createHtmlVideoFragment()` 把出片拆成五个算子，正好说明了渲染是怎么做的：

```
compile-program   html-program: compile(composition, timeline) → HtmlProgram
request-visual    need → capability htmlProgramCapabilities.rasterizeVisual   （帧序列）
compile-audio     media-operations: planAudio(composition, timeline) → 音频计划
request-audio     need → mediaOperationsProducers.renderAudio                  （混音）
request-mux       need → mediaOperationsProducers.mux(visual, audio)           （ffmpeg 封装）
project-video     output final.video
```

真正的帧来自 `packages/provider-html-local/src/provider.ts: createLocalHtmlProvider()` → `render.ts: rasterizeHtmlProgram() / rasterizeHtmlFrames()`：**用 Headless Chromium（托管下载 headless shell）把 HTML 动画逐帧栅格化**，配合 `concurrency.ts / ordered-frame-sink.ts` 管并发与顺序，再交给 `packages/media-local`（ffmpeg）编码与混流。README 里"64 个无头 Chromium 进程并发渲染"就是这个池。

**结论：画面是 HTML/CSS/JS 画的，不是拍的不是生成的。** 这是它相对"纯生成流"的最大成本优势 —— 字幕、板子、动效、卡片全部零模型费用。

### 4.4 字幕 / B-roll / 特效

| 能力 | 包与关键文件 | 形态 |
| --- | --- | --- |
| 字幕数据 | `@hypit/caption`、`@hypit/script` | CaptionDocument（词/对齐单元/cue），无时间 |
| 字幕定时 | `@hypit/narrative-caption`：`narrative-caption:Timing` | 把文档 + 对齐投影 → 逐词时间 |
| 字幕渲染 | `@hypit/caption-fine`：`render.ts`(55 KB)、`schedule.ts`(7.5 KB)、`style.ts`(19.6 KB)、`manifest.ts`(35 KB) | **自研布局/描边/卡拉 OK 盒/lead-tail 帧/换行**，配 `.svs` 里 ~60 个样式旋钮（`karaoke: current`、`active-box-*`、`cue-enter-frames`…） |
| B-roll | `@hypit/visual-track`：`surface.ts`(33 KB)、`layers.ts`(14 KB)、`lower.ts`(14 KB)、`motion.ts` | Clip + Frame + `Motion/Pose` 关键帧（`at="6f"`、`at="end-4f"`）+ `treatment` recipe |
| 动效/图形 | `@hypit/text-fine`、`@hypit/composition`、`@hypit/ranking`、`@hypit/comment-sticker`、`@hypit/interview-emoji-reveal`、`@hypit/depth-stack` | 专有组件，按"爆款格式"硬编码（`ranking/schedule.ts` 45 KB、`render.ts` 31 KB、`manifest.ts` 58 KB） |
| 合成 | `@hypit/film`：`decodeFilmSurface()` + `sealFilmProgram()` | 一个 Timeline + Canvas → Composition，Track 按 z 叠 |

### 4.5 依赖哪些生成模型

模型定义在各自的 `packages/<model>/src/index.ts`（用 `sealGenerationPortTable` 声明"端口表"），**服务在 Provider 里**：

| 类别 | 模型（源码里的确切 id） | 包 |
| --- | --- | --- |
| 图像 | `gpt-image-2`、`nano-banana-2`、`nano-banana-pro`、`seedream-5-lite`、`wan-2.7-image`、`wan-2.7-image-pro` | `gpt-image` / `nano-banana` / `seedream` / `wan` |
| 视频 | `seedance-2`、`seedance-2-fast`、`seedance-2-mini`、`seedance-2.5`、`minimax-h3`、`pixverse-v6`、`pixverse-c1`、`grok-imagine-video`、`grok-imagine-video-1.5-preview` | `seedance` / `minimax-h3` / `pixverse` / `grok-imagine` |
| 语音 | `voice-design-1`、`voice-clone`（Fish Audio）、`mimo-v2.5-tts-voicedesign`、`mimo-v2.5-tts-voiceclone`、`eleven_ttv_v3` | `fishaudio-speech` / `mimo-speech` / `elevenlabs-speech` |
| 对齐 | WhisperX（本地 Python 或托管） | `whisperx` / `provider-whisperx-local` |
| 抠像 | `matte-portrait-video`（火山） | `volcengine-matting` |
| 网关 | HypiHub（默认）、HiAPI、Monid、Pollo、Sume、BeatAPI、TokenDance | `provider-*`（可选 npm 包，非默认依赖） |

**关键点：模型与 Provider 是解耦的。** `docs/guide/providers.md` 明确写"模型定义你问什么、Provider 知道怎么问某个服务"，写一个新 Provider 用 `defineEndpoint`（`packages/endpoint/src/index.ts`），异步任务用 `submit → poll → collect`（`wakeAfter()`）。所以**接我们自己的推理服务是"写一个包"，不是改内核**。

### 4.6 能否离线 / 自托管

| 能力 | 离线？ | 依据 |
| --- | --- | --- |
| 编译、校验、plan | ✅ | `hypit check/plan` 不联网、不执行 |
| 字幕 / 动效 / 代码渲染 / 编码 | ✅ | README 原文："字幕、动效和代码渲染的画面，不调用生成模型也能编译成一条成片" |
| 生成（图/视频/语音） | ❌ 需自建或托管 | 有 Provider；本地推理要自己起服务并写 Provider |
| 语音对齐 | ✅ 但重 | `provider-whisperx-local`（uv + Python + 模型权重） |
| 人脸/区域分析 | ✅ 但重 | `provider-image-opencv-local`（Python OpenCV） |
| 部署形态 | 单机即可 | `hypit runtime up` 起本地 Worker（SQLite 状态），结果落 `.hypit/results/<date>/<build-id>/`；文档明确"整台 Runtime 搬到那台主机"，不拆队列 |

**资源清单（自托管要准备的）**：Node ≥ 22.15、pnpm、Chromium headless shell（约百 MB，可配 `browserCacheDirectory`）、ffmpeg/ffprobe、可选 uv+Python（WhisperX / OpenCV）、磁盘（每条 Build 的帧+素材，量级数百 MB～GB）。

### 4.7 许可证：逐条落到 VisionQA 上

`LICENSE` 是"改过的 Apache-2.0 + 附加条件"，原文要点与我们的判定：

| 条款 | 原文要点 | 对 VisionQA 的判定 |
| --- | --- | --- |
| 允许 | 自己基础设施上自用；为本组织（含为客户）做商业工作；单租户部署 | **内部/单租户：可以直接用**（含拿它给客户出片） |
| 1a 多租户 | 一个 tenant = 一个 workspace；两个及以上外部主体各持独立 workspace 即构成多租户，**收不收费都算** | VisionQA 有账号 + 每人自己的模板/画布 → **对外提供 = 多租户 = 需书面许可** |
| 1b 商业再分发 | 不得为商业获利出售/授权/随产品提供给第三方；**fork 与改源码可以，但须同许可且不得商业获利** | 把 hypit 当 VisionQA 的一个付费能力/打包进交付物 = **需许可** |
| 1c 品牌 | 不得删除或修改 CLI、run report、manifest 及"由此衍生的用户可见面"上的 Hypit 名称/LOGO/版权 | 若我们转售/贴牌，**这一条会直接冲突**（除非不使用这些面） |
| 2 贡献者 | 作者可调整开源协议严格度；贡献代码可用于其商业业务 | 我们若回馈代码，等于同意被用于其云业务 |
| 3 产出归属 | 用 Hypit 做出的视频/音频/图/manifest **归你**，不附加条件 | 客户成片归属没问题 |

补充事实（法务要对一下）：npm 上 `@hypit/hypit@0.3.1` 的 `license` 字段是 "SEE LICENSE IN LICENSE"（即上面的条件许可），但**早期版本（如 0.0.1）元数据记的是 `Apache-2.0`** —— 同一包不同版本的许可元数据不一致，用哪个版本要按该版本附带的 LICENSE 为准。

**风险定级：高（法务级，不是技术级）。** 建议在写第一行整合代码前先拿到两点书面结论：（1）内部单租户 PoC 是否算 "for your own organization"；（2）对外 SaaS 的商业许可报价与品牌条款能否接受。

## 五、与 VisionQA 现有链路的对照

VisionQA 现在的链路（`docs/replication-pipeline.md`）：

```
爆款雷达 → 一键复刻（POST /api/replicate）
  → server/media.mjs: acquireVideo()       解析/下载
  → server/frames.mjs: probeVideo / detectSceneCuts / planTimestamps / extractFrames
  → server/vision.mjs: analyzeFrames()     一次喂 4–18 帧，出严格 JSON
  → server/templates.mjs: createTemplate() 入 data/templates.json + data/frames/<id>/
模板库 → 送去评审 → server/review.mjs: reviewVisual() → verdict + observations(含 0–1 证据框)
```

| 维度 | VisionQA 现状 | Hypit | 差距性质 |
| --- | --- | --- | --- |
| 时间表示 | **秒**（`startSec/endSec`），由抽帧给出 | **词/句/瞬间锚点**，秒是投影结果 | 结构性差距（改台词即全废 vs 自动重排） |
| 声音 | **听不到**（`docs/replication-pipeline.md`："视觉模型分析只看画面，听不到声音"） | `hypit transcribe` + `whisperx:Alignment` 词级时间 | 可补，但成本在 ASR |
| 执行模型 | 一条线性函数链，单进程，内存 job（`jobs.mjs`，保留 40 条） | 有类型的图 + plan + 事件溯源 + 本地 Worker | 架构级差距 |
| 复用 | 无（重跑 = 重来） | `build-record` + `satisfy` 显式钉 Output | 直接影响"100 个变体"的成本 |
| 出片 | **没有**（"用模板生成新内容"标注为未做） | 有（HTML→Chromium→ffmpeg） | 能力缺口 |
| 评审 | **强**：visual-baseline 七维、verdict、像素锚点、provider 降级链 | **弱**：只有 `review.md` 的文字建议，无机器判决 | **我们的护城河，不要被替换** |
| 成本可见性 | 积分自定（`credits.mjs: priceOf()`） | `hypit pricing --json` 读 Provider 真实价目 | 可借 |
| 中文 | 有（模板字段、评审中英混排） | 有（字级切词、Noto Sans SC fontsource） | 基本对齐 |

**核心结论：Hypit 补的是"生成与执行"，VisionQA 强的是"检索与评审"。两者互补，不是替代关系。** 因此融合方向应该是"**把 Hypit 塞进 VisionQA 的执行位（后端），把 VisionQA 的评审挂到 Hypit 的结果上**"，而不是把 VisionQA 的产品模型改成 SVML-first。

## 八、三条可选的路线（含放弃理由）

### 路线 A：借壳（推荐先做）
VisionQA 保持现在的前端与 product 语义，把 `hypit` 当"本地渲染/生成后端"（类似 `ffmpeg-static` 的地位）。改动集中在 `server/hypit.mjs` + 一个 `RuntimeAdapter`。
- **放弃的**：graph-first 的增量重算、跨片素材复用、Studio 的时间轴编辑。
- **代价**：多一个外部进程 + Node/Chromium 依赖；体验上"复刻"仍是"提交-等待-出片"，不是"边看边改"。

### 路线 B：借语义（推荐第二步）
把"锚点时间轴 + 显式复用"移植进 VisionQA 自己的 JSON 模型（不引入 SVML 作为主存储）。
- **放弃的**：SVML 的完整表达力（它有上百个 Surface，我们只抄 15 个概念）。
- **代价**：要自己维护一套 anchor→frame 的投影（约 800–1500 行），并且要跟 ASR 的稳定性绑在一起。

### 路线 C：整体替换（不建议）
用 hypit 的图做 VisionQA 的主干，前端改成 Studio 伴生。
- **放弃的**：现在的检索/雷达/模板库/评审链路要重写；品牌条款 1c 直接冲突；多租户要商业许可。
- **结论**：除非公司决定"转向视频制作工具"，否则不划算。

## 九、未验证与待确认（诚实边界）

1. **一次 build 都没跑。** 本机没装 `@hypit/hypit` 依赖、没有 Chromium 池、没有任何 Provider 凭证（HypiHub / HiAPI / Pollo… 全无）。**第四节的执行结论全部来自源码与文档，不是实测。**
2. **例子能否开箱跑未知。** `examples/ranking-football/assets/` 在 `.gitignore` 里被忽略却在工作区存在（本次浅克隆拿到了）；`hypit.runtime.json` 默认端点指向 HypiHub，没账号跑不动。README 的"$1.15 一条"是作者账单，不是我们的实测价。
3. **渲染速度/质量未测。** "64 并发 Chromium"是 README 说法；Windows 上（我们的部署环境）能开多少、内存吃多少、长路径会不会炸，仓库 CI 只覆盖"能否跑通"，不覆盖产能。
4. **中文断行未测。** `caption-fine` 有 `wrap: word / max-words-per-line`，但示例全是英文；中文按字切分后"一行几字"的实际观感要真跑一次。
5. **版本漂移是实锤。** 三个月内 0.3 → 0.3.1 → 0.3.2，仓库里就有 `migrations/0.3.md` 与 `migrations/0.3.1.md` 两份迁移指南；`markup@1` 的 Surface 语义仍在动。任何依赖它做长期契约的整合都要**钉死版本 + 写契约测试**。
6. **许可证判定需要法务。** 我按 LICENSE 文本给出的是"技术人员解读"：`tenant = workspace` 套到 VisionQA 的"每用户一套模板库/画布"上，几乎必然构成多租户。**但这是法律判断，不是我的结论。**
7. **npm 元数据与仓库 LICENSE 的历史版本不一致**（0.0.1 记 Apache-2.0，0.3.1 记 SEE LICENSE IN LICENSE），用哪个版本按该版本 tarball 里的 LICENSE 为准。
