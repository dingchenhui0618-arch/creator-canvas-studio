# TypeSafe Jev 用于 VisionQA 视觉评审的可行性调研

日期：2026-11-11 · 状态：**只读调研，未改任何代码** · 结论：**现在不能直接落地生产评审；可以作为"低成本初筛 + 证据锚点"的 P0 试验，前提是先拿 API Key 跑一轮实测**

## 一、结论先行

1. **能力上是对得上的，但差两块东西**：Jev 1.14 确实读图，且四种原语里的 **Box 返回的归一化 bbox（0–1 分数，左上原点）和 VisionQA 的 evidence 字段几乎一模一样**；Noul / Score / Choice 返回带 calibrated 概率与 confidence 的枚举化答案，正好能当"能不能投 / 多严重 / 哪个维度"的机器判据。
2. **缺口一：Jev 不产出文字。** 它不写 statement、不写 fixes、不写 summary。而工作台现在的契约（`server/review.mjs` 的 `normalize()`）要求 `summary` + 每条 observation 的 `statement` + `fixes`。这些要么由代码按 (维度, 严重度) 模板拼，要么仍交给 DeepSeek 写。
3. **缺口二：图像能力官方自己标着 "Dreamer-ready"。** 文档原文：images 与 Box questions "aren't yet up to our standards to call ready for production"，请求格式、答案、限制**会在版本间变化**，准确率会随后续模型更新而变。也就是说：不能把 Jev 的视觉结论写成对外承诺。
4. **本机零凭证、零 SDK。** 扫描 `D:\Projects\creator-canvas-studio` 与用户 home 下配置，无 `TYPESAFE_API_KEY`、无 `@typesafe-ai/sdk`（详见第三节）。因此**第 3 步的"最小调用验证"做不到**——我做了两次真实探测，两次都是 `403 authentication_error`，只能证明端点可达与鉴权口径，不能证明它"能返回结构化判断"。
5. **给 lead 的一句话**：这不是"能不能用"的问题，是"值不值得现在花一次注册成本去验"的问题。**建议先申请一个 Key，用 20 张本仓库真实首帧跑一次对照（Jev 判决 vs 现有 DeepSeek 判决），再定要不要接。** 在那之前不要写生产代码。

## 四、实测记录（能测的都测了）

### 4.1 端点与鉴权口径

```
GET  https://api.typesafe.ai/v1/models      -> HTTP 403  (1.02s)
POST https://api.typesafe.ai/v1/systemone   -> HTTP 403  (0.40s)
body: {"detail":{"error_type":"authentication_error",
       "message":"Must supply an API key! Check your request and try again."}}
header: x-typesafe-request-id: req_01a1c8c556817b5f995c1a584d930c1f / server: cloudflare
```

- **能确认的**：域名与路径正确、Cloudflare 可达、缺 Key 时返回结构化 403 而不是 404/5xx、每个响应带 `x-typesafe-request-id`（排障可用）。
- **不能确认的**：任何模型行为——结构化输出形状、图像是否真被读懂、延迟、准确率。**要验证必须真有 Key。**

### 4.2 网络基线（本机 → api.typesafe.ai，5 次取稳定值）

| 阶段 | 耗时 |
| --- | --- |
| DNS | 0.018–0.049 s |
| TCP connect | 0.020–0.051 s |
| TLS 握手完成 | **≈ 0.20 s** |
| 首字节（TTFB） | **≈ 0.40 s**（含 403 鉴权判定） |
| 出口区域 | LAX（cf-ray 尾部 -LAX），本机到边缘绕了一段 |

这份数据只说明**每次调用固定要付 ≈0.2 s 的握手 + 若干 RTT**，与模型算力无关；换成长连接（keep-alive）可以摊掉大部分。

### 4.3 文档给出的性能承诺

- 「Most calls complete in about **100 ms**」「fast enough for real-time request paths」——**这是文本场景的口径，文档没有给带图请求的延迟数字**。
- 「Adding questions barely changes the response time」「每个 question 独立并行评估」——意味着**多问几个维度不会线性变慢**，这是它相对"一次 LLM 调用出全部结论"的最大结构优势。
- 「We'll be providing guidance on estimating image token usage soon」——**图像 token 数官方还没给估算口径**，所以第六节的单次成本只能是区间估计。

## 五、Jev 到底能对图像做什么（能力与硬限制）

### 5.1 四种原语，逐一对到评审需求

| 原语 | 答案形状 | 在视觉评审里的用法 |
| --- | --- | --- |
| **Box** | `{top,bottom,left,right}` 各 0–1 + `confidence` | **定位问题区域**。值就是"相对图片宽高的分数，左上原点"，和 VisionQA 的 `evidence{x,y,w,h}` 是同一坐标系，`x=left, y=top, w=right-left, h=bottom-top` 一行换算即可 |
| **Noul** | 单个 0–1 概率（是/否，无 confidence 字段） | "这张首帧能不能当封面""主体是否被裁掉"这类闸门；多个可能同时成立的标签就一个标签一条 Noul |
| **Score** | 概率加权的位置分 + 每档概率 + confidence | 维度打分（层级/对比/间距…），**跨条目可比**，适合排序 |
| **Choice** | 选中项 + 全选项概率分布 + confidence | 枚举化判定："最严重的问题属于哪一类""裁切受损程度档位" |

三种判断成立时：**Noul 做闸门 → Score 做排序 → Choice 做归因 → Box 出锚点**，四条一起发，一次请求并行出结果（对应技能里的 "speculative fan-out" 模式）。

### 5.2 硬限制（会直接决定接入形态）

| 限制 | 值 | 对我们的影响 |
| --- | --- | --- |
| 图片格式 | 仅 PNG / JPEG（静止帧），动图拒绝 | 抽帧必须转 JPEG；现有 `MEDIA_MIME` 还认 `.webp`，**送 Jev 前必须转码** |
| 边长 | 单边 **280–1568 px**，越界**直接拒绝、不自动缩放** | 抽帧要保证 ≥280px；4K 首帧必须缩到 ≤1568 |
| 单图体积 | ≤ 16 MiB | 一般够 |
| 请求总体积 | 32 MiB（含 base64 膨胀与多图展开） | 一次最多 1 候选 + 2 参考，不要整段多帧塞一单 |
| 每请求上下文 | 64k（开 Long-Context 头可到 262k，但更慢更不准） | 够用 |
| 图像开关 | 必须带 `TypeSafe-Danger-Zone-Images: true`，否则 400 | 忘了这个头就是 400，不是静默降级 |
| **成熟度** | **官方标 "Dreamer-ready"：格式/答案/限制随版本变，准确率随模型更新变** | **不能写进对外 SLA，也不能当作验收的唯一依据** |

### 5.3 一个关键结构性事实

Jev **不生成文字、不解释推理**。这是它快和便宜的原因，也是它在"视觉评审"这个场景里的根本边界：

- 现在的契约里 `observations[].statement`（"问题描述"）和 `fixes[].detail`（"具体怎么改"）都是给人读的**自然语言**，Jev 一个字都不会写。
- 也就是说：**Jev 能给"判断"，给不了"说法"**。任何"用 Jev 替换 DeepSeek 评审"的方案都不成立；只能是两者分工。

## 六、接入设计（如果决定做）

### 6.1 放在哪一步：初筛 + 打分 + 锚点，不放在最终判定

现有链路（`server/review.mjs`）是：插件服务 → 不可达则 `local-model:deepseek-flash` 一次性出完整 JSON（实测 72–84 s）。建议改成三段：

```
①  Jev 快判（新增，1 次请求）
    Noul  x3  : 主体是否完整 / 文字是否可读 / 是否可作封面
    Score x3  : 层级 / 对比 / 间距   <- 同一组 levels 保证可比
    Box   xN  : 疑似问题区域（只对判否的维度问）
        |
        v  typed answers + confidence
②  代码判定（确定性，可测试、可调权重）
    verdict = 阈值表(Noul 概率, Score 档位, confidence)
    低置信 -> escalate
        |
        v
③  DeepSeek 收尾（只产出人读的东西）
    输入：原图 + ① 的结构化信号（当"已知事实"喂进去，别让它重新发明判断）
    输出：statement / fixes / summary 文案
```

**为什么是这个顺序**：Jev 快且便宜、多问不线性变慢，适合当闸门；DeepSeek 慢但会写字，适合收尾。反过来（先 DeepSeek 再 Jev 校验）一分钟都省不下来。

### 6.2 契约字段映射

| VisionQA 字段 | 来源 | 说明 |
| --- | --- | --- |
| `verdict` | **代码**（阈值表，输入是 Jev 的 Noul/Score） | 不让模型直接给 verdict，规则留在代码里才可审计 |
| `observations[].dimension` | 代码（question id 映射） | Jev 的 question id 就是维度名，代码里固定映射 |
| `observations[].severity` | Choice 最高概率档，或 Score 档位 → 严重度表 | 档位要在代码里定，别让模型自由发挥 |
| `observations[].statement` | **DeepSeek 写**；或代码模板（维度+档位 → 中文句子） | **Jev 给不了**，这是必须承认的缺口 |
| `observations[].evidence` | **Box**（唯一能出像素锚点的通道） | 换算见 5.1；`confidence < 0.6` 时按文档建议扩边后再裁 |
| `observations[].confidence` | 对应原语的 confidence | Noul 没有 confidence，只有概率——**Noul 的概率不是"强度"**，别当严重度用 |
| `fixes` | DeepSeek 或模板 | 同上 |
| `notAssessable` | 代码：判据不满足时（如缺投放尺寸）确定性生成 | 比靠模型自觉更稳 |
| `provider` | 新增标注，如 `jev@1.14.0+deepseek-flash` | 沿用现有"绝不冒充"的原则 |
| `signals` | **新增（可选、加性）**：把 Jev 原始答案整块带出 | 便于后面调权重与做回归，不影响老前端 |

改动面很小且是加性的：`normalize()` 增加 `signals` 透传与 `evidence` 换算；`reviewVisual()` 前面插一段 Jev 调用；前端只用新增字段可选展示。**但目前一行都还没改（本任务只读）。**

### 6.3 与现有 DeepSeek 视觉评审怎么配合

- **分工不互斥**：Jev 出"结构信号"，DeepSeek 出"人话 + 修正建议"。两个结果落进同一条 review 记录（`server/reviews.mjs` 已按账号存最近 200 条）。
- **DeepSeek 从"唯一判据"降级为"文字层 + 兜底判据"**：Jev 不可用或低置信时，DeepSeek 的结果照旧当完整结论（就是现在这条路径，不用改）。
- **互相校验而不是互相覆盖**：两者对同一维度结论相反时，直接标 `needs_review` 并把分歧写进 `signals`——比让任一模型单独拍板更诚实。

### 6.4 失败回退（按现有代码风格来）

现成的降级链（`llm.mjs` 的 `callTextModel` 多模型 + 重试 + `extractJson` 兜底）已经证明这套模式好使，Jev 段照抄同一套语义：

| 情况 | 处置 |
| --- | --- |
| 无 Key / 401 / 403 | 跳过 Jev，走现有 local-model，`provider` 标注不变 |
| 400（忘带头 / 图被拒 / 超上下文） | 记 warning（含 `x-typesafe-request-id`）后降级；**不要重试同一张图** |
| 429 | 读 `retry-after`，只退避重试 1 次；仍失败降级（评审是交互路径，不能长挂） |
| 超时 | 单次硬超时建议 **8 s**（远大于文本 100ms 口径，给带图留余量），超时即降级 |
| 单条 confidence 过低 | 该条不进 `observations` 的 blocker/major，塞 `notAssessable` |
| 图片不合规（webp / <280px / >1568px） | 服务端先转码缩放；转码失败就不调 Jev |

**原则**：Jev 段永远不能是唯一通路，任何失败都必须能落到当前已跑通的链路，且 `provider` 不许说谎。

### 6.5 成本与延迟

**单价**：$42 / Btok = **$0.042 / Mtok，只收输入，输出免费**（1.13 与 1.14 同价）。

**单次估算**（图像 token 官方未给口径，以下按 1–2k token/图 假设，**需实测校正**）：

| 组成 | 估算 token | 成本 |
| --- | --- | --- |
| 指令 + 判据 + 问题 | 0.5–1 k | — |
| 1 张首帧（1568px） | 1–2 k（假设） | — |
| **合计** | **≈ 2–3 k** | **≈ $0.0001** |

即使按 10k token 算也只有 $0.0004/次。**成本不是问题**——真正的问题是延迟与可靠性还没实测。

**延迟**：

| 项 | 数值 | 来源 |
| --- | --- | --- |
| 文本请求 | ≈100 ms（官方口径） | 文档 |
| 带图请求 | **未知** | 文档未给 |
| 本机固定开销 | TLS ≈0.2 s + 每次 2 RTT | 本次实测 |
| 对比：现有 DeepSeek 评审 | **72.9 s / 84.2 s（实测）** | `docs/review-integration.md` |

如果带图 Jev 真在亚秒到 3 s 量级，它能把"评审要等一分多钟"变成"先出结论、文字后补"，这是**体验上唯一真正值钱的收益**；如果带图要十几秒，收益就只剩"多问不线性变慢"，价值大幅下降。**这个数字必须实测，猜没有意义。**

## 七、现在能不能落地

**结论：不能作为生产评审的主判据；可以作为实验性初筛，且必须先有 Key。**

### 现在可落地的（0 开发量）
- 无。**没有 Key 什么都不能做**，包括写集成代码——真实返回没见过，写出来就是猜。

### 需要先拿什么（按优先级）

1. **TypeSafe API Key**（https://console.typesafe.ai/keys ）。这是唯一硬阻塞。文档未说明是否有免费额度/试用，**注册与是否产生费用需要你确认**——花钱的事我不替你做主。
2. Key 到手后跑**一次真实验证**（原任务第 3 步，现在欠着）：取 1 张本仓库真实首帧（`data/frames/` 已有），一次请求同时发 Noul×2 + Score×2 + Box×1，记录：HTTP 状态、`model` 版本串、`usage.input_tokens`、端到端延迟、答案是否合 schema、Box 是否指到真问题。**验收标准：5 s 内返回、字段齐全、Box 落在人眼认可区域 ≥ 3/4 张图。**
3. 20 张图小对照集：Jev 判决 vs 现有 DeepSeek 判决 vs 人工标注。**没有这一步，"接进来"只是把不确定性从 DeepSeek 搬到了 Jev。**
4. 一个要 lead 拍板的决定：**是否接受"图像能力 Dreamer-ready"这件事**。如果评审结论要给外部客户看，按官方目前的成熟度声明，我建议**只当内部信号，不对外呈现**。

### 明确不建议做的
- 不要让 Jev 直接产出 `verdict` 或 `severity`（它给不了文本，硬拼出来的判定不可审计）。
- 不要撤掉现有 DeepSeek 链路（72–84 s 慢，但它是唯一能写"人话修正建议"的通道）。
- 不要一次请求塞多帧（`maxFrames` 18 帧）：32 MiB 展开限制与准确率都会崩；多帧请一帧一单并行发。
